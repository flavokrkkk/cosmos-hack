# Как выигрывать Кейс 02 — наш угол

_База знаний Кейса 02 · [← индекс](README.md)_

Большинство принесёт слайды и качественные рассуждения. Наш отрыв — **работающая количественная
модель + интерактивный инструмент**, обёрнутые в строгую экономическую аргументацию:

1. **Движок портфеля** (config-driven): 8 лотов как объекты (CAPEX, OPEX/год, спрос, общественная
   ценность, риск, масштабируемость, срок) → выбор 4 + режим + финансирование на лот → **скоркард**
   под бюджетом: затраты по годам, покрытие общественной ценности, устойчивость (нужная субсидия /
   NPV / точка безубыточности), индексы конкуренции и масштабируемости, риск-экспозиция.
2. **Перебор всех 70 портфелей (8 по 4) × режимы → Парето-фронт.** Показываем, что наш выбор
   на фронте, и почему именно он при заданных весах. Экономисты это уважают.
3. **Синергии** — cross-lot разделение затрат (общий наземный сегмент, данные, платформа).
4. **Дорожная карта как переходы режимов** + glide-path субсидии по годам.
5. **LLM (qwen3, уже в каркасе)** — генерирует нарратив на основе чисел модели: обоснование
   по лоту, текст дорожной карты, риск-меморандум. Не «из воздуха», а из скоркарда.
6. **Сдача:** живой инструмент (демо) + отчёт (recommendation-first, таблица допущений,
   методология, портфель + Парето-обоснование, sensitivity, отвергнутые лоты, роадмэп, риски) + питч.

**Роли:** владелец экономики (защищает модель и допущения — критично) · билдер движка (бэк +
LLM-ручка) · фронт (дашборд: селектор лотов, скоркард, radar, Парето-плот) · питч-владелец.

⚠️ Инструмент усиливает хорошую экономическую модель, но не заменяет её. Жюри будет долбить
допущения — их надо уметь защитить.

## Что именно строим: данные → движок → дашборд (предложение 2026-09-11, обсудить с командой)

**Датасета в этом кейсе нет — и не должно быть.** «Данные» здесь = **параметры лотов + допущения +
сценарии**, и у каждого числа есть происхождение: `постановка` (дали организаторы) / `ресерч` (URL,
см. [research/](research/README.md)) / `допущение` (наше, обосновано). Стартовый набор уже есть —
[research/engine-parameters.md](research/engine-parameters.md). Риск не в «нет данных», а в
**несогласованных или бессточных числах** → лечится полем `source` у каждого параметра и единой
нормировкой (млрд ₽, в год, горизонт).

### Три слоя + LLM

1. **База параметров** — JSON/YAML в репо (версионируемо, диффуемо, судья может открыть); Postgres —
   только для сохранённых сценариев/портфелей. Сущности:
   - `Lot` — id, name, category, `capex`, `opex_year`, `demand`, `benefit_year`, `time_to_effect`,
     `lifetime`, `market_readiness`, `lock_in`, `budget_dependence`, `sources[]`;
   - `Stakeholders` — шесть ролей на лот (получатель ценности / пользователь / плательщик / заказчик /
     оператор / поставщики), см. [01-case02-brief.md](01-case02-brief.md). Именно несовпадение
     «получатель ↔ плательщик» объясняет выбор режима;
   - `AccessMode` — `public_core | club | market_emergency` → правила: множитель адопции, доля
     платного спроса, стоимость аварийного слоя;
   - **`Procurement` ≠ `Funding`** (важное разделение, §9.1 [notes/2026-09-10](notes/2026-09-10-teammate-case02-hypothesis.md)):
     - `Procurement` — *как выбирается исполнитель и за что ему платят*: `dev_contract |
       service_subscription | availability_payment | payment_by_result | framework_multi_supplier |
       component_tender | long_term_with_milestones | guaranteed_minimum | joint_club_purchase`;
     - `Funding` — *откуда деньги*: `federal_budget | regional_budget | grants | operator_capex |
       club_fees | user_tariffs | premium_analytics | anchor_state_order | infra_co_financing |
       cross_subsidy`;
     - конкретную правовую форму (офсетный контракт ст. 111.4 44-ФЗ, ГЧП/концессия по ФЗ-196, РУО,
       форвардный выкуп данных — [research/ru-service-model.md](research/ru-service-model.md))
       подставляем **только там, где она действительно подходит структуре лота**, а не называем
       концессией любую совместную схему;
   - `Risk` — type, owner, p, impact, mitigation; `Scenario` — budget, horizon, discount_rate,
     weights, overrides.
2. **Движок** (FastAPI, синхронно — вычисления лёгкие): на лот — денежные потоки по годам, нужная
   субсидия, NPV/окупаемость, **пять групп показателей** (§17 [notes/2026-09-10](notes/2026-09-10-teammate-case02-hypothesis.md)):
   *общественная ценность* (охват, покрытие критических функций, снижение ущерба), *экономическая
   устойчивость* (TCO, бюджетная нагрузка по годам, доля небюджетных доходов, дефицит), *конкуренция*
   (число поставщиков, стоимость смены оператора, переносимость данных, концентрация), **надёжность**
   (SLA, резервный поставщик, время восстановления, аварийная мощность, единичные точки отказа),
   *масштабируемость* (стоимость нового региона/пользователя, повторное использование инфраструктуры).
   Интегральный балл — только как навигация, рядом всегда исходные значения, формула и trade-off;
   портфель — сумма + **синергии** (cross-lot затраты) + бюджетное ограничение; **перебор 70 портфелей
   × назначения режимов → Парето-фронт**; **sensitivity** (торнадо по допущениям); **Monte Carlo**
   (сдвиг сроков, недобор спроса, перерасход) → распределения исходов, не точки.
3. **Дашборд** (React/TanStack): выбор 4 лотов + режим + финансирование → скоркард; потоки по годам с
   glide-path субсидии; Парето-плот с нашим портфелем; торнадо; сравнение портфелей; **бейдж
   происхождения у каждого числа**; ползунки допущений (бюджет, веса, ставка) — это и есть «динамика».
4. **LLM** (qwen3, готовый `OllamaService`) — только текст из чисел: обоснование лота, дорожная
   карта, риск-меморандум, «объясни этот сценарий». **Числа LLM не генерирует.**

### «Динамически предсказывать» = what-if, а не ML

Обучать нечего — истории портфелей не существует. Честная и более убедительная для экономистов
форма — **прозрачная параметрическая модель + сценарии + Monte Carlo**: судья двигает допущение и
видит последствия. Чёрный ящик здесь минус, а не плюс.

### API (минимум)

`GET /lots` · `POST /evaluate {portfolio, scenario}` → scorecard + cashflows · `GET /pareto?scenario` ·
`POST /sensitivity` · `POST /narrative` (LLM). Всё синхронно; Monte Carlo — в Taskiq, только если >1–2 с.

### Воспроизводимость: приём, унаследованный от NDVI-кита

Классический ML не нужен (обучать нечего, автометрики нет — п. 14.2), но **дисциплина из снятого
`ml/` переносится целиком** — Положение требует воспроизводимости (п. 9.4), а жюри-экономисты будут
проверять цифры:

- **параметры отдельно от кода** — правишь конфиг, а не логику;
- **`selfcheck` для движка** — батарея проверок, которая доказывает: те же входы → те же выходы;
  бюджетное ограничение действительно соблюдается; суммы по годам сходятся; Парето-фронт содержит
  выбранный портфель; ни одно число не берётся из LLM. Запускается одной командой, ненулевой код при
  падении. Это же — аргумент на защите: «наши числа воспроизводимы, вот тест»;
- **у каждого параметра — происхождение** (`постановка` / `ресерч` / `допущение`), видимое в UI и в отчёте.

Сам код кита — в истории, тег `ndvi-kit` (`git checkout ndvi-kit -- ml/`), если понадобится подсмотреть
структуру.

### Чего не строить

BI-панель с внешней статистикой «для красоты»; ML-«предсказатель»; live-скрапинг; генерацию чисел LLM.

### Открытые вопросы к команде

- Хранение параметров: JSON в репо (предлагаю) vs таблицы в Postgres с сидом.
- Нужны ли многопользовательский режим и сохранение сценариев (auth есть) — или демо-сессии достаточно.
- Глубина Monte Carlo: какие параметры считать случайными и с какими распределениями.
