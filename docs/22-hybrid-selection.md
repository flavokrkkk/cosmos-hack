# Принятый алгоритм: денежное ограничение и maximin

**Статус:** принят пользователем 12.09.2026; единственный метод приложения и автономного CLI — `hybrid_maximin_v1`. Старые методы выбора удалены из исполняемого кода команды. Канонические материалы организаторов не менялись.

**Решение по итогам обсуждения:** leximin отклонён, D остаётся вне рабочего поиска. Сохраняется Q → S при автоматическом Δ и денежное отсечение перед Q при явном Δ. Дополнительные сценарии выделены в отдельный этап после основного решения; тест проверяет, что их отключение или изменение не меняет победителя, границы шкал и этапы основного отбора.

## Правило выбора

**ФАКТ постановки:** организаторы не задают скрытой формулы победителя. Нужно выбрать четыре различных лота, проверить девять ограничений BASE/STRESS и обосновать решение. [Источник, разделы 7, 12–13](https://github.com/SpaceEconomyPolicy/test).

**Решение команды / допущение:** защищаем наиболее слабый из шести критериев: VPUB, S = CASH − OPEX, C0, readiness, resilience, scale. C0 минимизируется, остальные максимизируются. OPEX, KCASH и t_rep остаются в каноническом расчёте и ограничениях; отдельно в Q они не входят. Индекс t_rep не называется тиражируемостью: для этого в данных есть scale.

1. Вычислить все сочетания четырёх лотов и режимов A/B/C. На текущих входах это 5670 конфигураций.
2. Зафиксировать шкалы по всей официально допустимой области выбранного сценария. По умолчанию требуются одновременно BASE и STRESS: 143 варианта. Для BASE без требования STRESS — 1031.
3. Применить явные дополнительные требования: область лотов, лимит C0, минимум VPUB, обязательные лоты общественного ядра. Шкалы при этом не менять.
4. Найти Smax в оставшейся области. Оставить S ≥ Smax − Δ.
5. Вычислить Q = min(z_VPUB, z_S, z_C0, z_readiness, z_resilience, z_scale), найти максимум Q среди оставшихся.
6. ε качества равен 0: выбрать точный максимум Q. При равенстве выбрать максимум S; при равных Q и S — максимум суммы шести оценок; при полном равенстве — лексикографически наименьший ID состава.

Сумма оценок используется только для последнего содержательного разрешения равенств: она не заменяет Q взвешенным средним. Это исключает выбор доминируемого варианта при равных Q и S в принятой точности.

## Нормирование и точность

Для максимизируемого критерия z = (x − xmin)/(xmax − xmin), для C0 z = (xmax − x)/(xmax − xmin). Если весь исходный диапазон постоянен, z = 1. Границы фиксируются до пользовательских фильтров, Δ и сценариев чувствительности. При шоках значения могут выходить за [0; 1]: их не обрезаем, чтобы не скрывать ухудшение.

**Допущение:** равноправными считаются улучшения относительно доступного диапазона каждого критерия. Это предпочтение команды, а не объективная важность критериев. Диапазоны readiness/resilience/scale узкие; min–max усиливает небольшие различия. Исследовательская проверка исходной шкалы 1–5 давала другой выбор — FIRE/AGRI/TRANS/ENV ABBA. Поэтому текущая рекомендация условна относительно принятой шкалы; она не объявляется универсально идеальной.

Канонические показатели не округляются при расчёте и экспорте. Для ранжирования агрегаты округляются до 8 десятичных знаков, после чего нормирование и сравнения выполняются рациональными числами. Это удаляет машинный шум суммирования, не вводя положительный ε качества. Шаг 1e-8 — вычислительное допущение, не оценка точности исходных данных.

Явно введённый Δ сохраняет десятичное значение, полученное интерфейсом, без дополнительного округления движком. Поэтому предел чуть ниже точки переключения не повышается до неё автоматически. Денежные пороги не принимают логические значения. CLI и API отклоняют неподдерживаемый метод вместо молчаливого запуска другого правила.

## Как выбран Δ без подгонки числа

**Допущение команды:** по умолчанию `cash_loss_limit_mrub = null`. Сначала определяем глобальный максимум Q в области после дополнительных требований. Затем:

`Δ* = Smax − max(S среди вариантов с глобально максимальным Q)`.

Это минимальная денежная уступка для достижения лучшего Q. Автоматический режим математически эквивалентен приоритету Q, затем S; денежное ограничение в нём не является независимым ограничением бюджета. Число 9,5 не зашито в код: оно получилось на текущих данных. Если заказчик задаёт независимый денежный предел, вводится числовой Δ; тогда гибрид может предпочесть более денежный вариант с меньшим Q. Δ = 0 допускает только максимальный S.

**Граница интерпретации:** Q — относительная оценка самого слабого критерия, а не процент выполнения общественной задачи. При равном Q другие показатели могут различаться. Гипотетические шоки и пробные ужесточения требований относятся к отдельным результатам чувствительности: они не меняют основную рекомендацию и не являются оценками вероятности. Аналитические запасы до нарушения официальных условий и до нулевого годового остатка показываются отдельно; нулевой остаток не вводится как новое обязательное ограничение кейса.

**НАХОДКА:** комбинация ограничений на цели и achievement scalarizing function / Chebyshev применяется в многокритериальном выборе; пример — [MultiOptForest, раздел Multi-objective optimization, формулы 2–3](https://doi.org/10.12688/openreseurope.15812.2), [документация DESDEO](https://desdeo.readthedocs.io/en/latest/explanation/scalarization/). Источники обосновывают класс метода, но не наши шкалы, конкретное Δ или шесть критериев. Автоматическое правило Δ* — наша явная политика выбора, а не перенесённая из статьи денежная оценка.

## Контрольный результат и цена баланса

**ФАКТ РАСЧЁТА:** [машиночитаемый результат](../results/hybrid_analysis.json), [канонические показатели](../results/portfolio_metrics.json), [входы](../config/decision.json).

Рекомендация: **FIRE:A, AGRI:C, TRANS:C, ENV:A**. Q = **0,5**; слабая оценка — scale. Автоматический Δ = **9,5 млн ₽/год**. Максимальный S в допустимой области — **101,75 млн ₽/год**; выбранный S — **92,25 млн ₽/год**.

- C0: **1129,8 млн ₽**; резерв STRESS: **50,2 млн ₽**.
- OPEX: **305,75 млн ₽/год**; CASH: **398,0 млн ₽/год**.
- VPUB: **1199,0 млн ₽/год** условной общественной ценности, не денежной выручки.
- KCASH: **1,301717089**; t_rep: **0,73**.
- readiness: **4,525**; resilience: **4,05**; scale: **4,675**.
- Четыре территориальных архетипа, две группы возможностей, два лота общественного ядра.
- Все девять проверок BASE и STRESS проходят для одного и того же состава.

При фиксированных шкалах точки смены победителя по Δ составляют 0; 2,25; 7,25; 9,5 млн ₽/год. Последовательность S: 101,75 → 99,5 → 94,5 → 92,25. Полные составы, полуоткрытые интервалы и Q находятся в `switching_curve` результата. Это полный проход точек смены на текущем множестве, а не подобранные вручную пороги.

Исторические FIRE ABBA (57,5) и FIRE ACBA (80,75) имеют тот же Q = 0,5 при основной шкале, поэтому уступают по следующему правилу — максимуму S. Их более высокий VPUB не отрицается: maximin не вознаграждает улучшения показателей выше самого слабого. Для иной управленческой цели нужен явно заявленный предел или пересмотр предпочтения, а не ручная замена победителя.

## Обоснование для защиты человеческим языком

**ГИПОТЕЗА управленческой схемы:** FIRE и ENV в общественном ядре дают информацию для защиты людей, лесов и окружающей среды; эффект не ограничивается теми, кто может заплатить за индивидуальную подписку. AGRI и TRANS имеют организационных пользователей, которым можно адресовать отдельные коммерческие продукты. Режимы разделяют способы доступа и финансирования. Названия и договорные границы этих продуктов — предложение команды; коэффициенты A/B/C взяты из кейса.

При принятом составе годовые остатки лотов: FIRE −5,50; AGRI +56,25; TRANS +44,00; ENV −2,50 млн ₽. Сумма — 92,25. Это возможность финансовой взаимодополняемости. Чтобы положительные поступления действительно покрывали общественные сервисы, договор должен разрешать соответствующие потоки, фиксировать приоритет обслуживания и предусматривать оборотные средства. Перевод денег внутри портфеля не увеличивает совокупный CASH.

Технически можно совместно использовать приём и каталогизацию данных, архив временных рядов, контроль качества, API и типовые интеграции. Это гипотеза организационной экономии: подтверждается архитектурой, сметой и измерением повторного использования. В расчёт не добавлено ни рубля бонуса синергии. География лотов различается: нельзя утверждать, что центральный TRANS уже обеспечивает эвакуацию для сибирского FIRE или что ENV измеряет последствия тех же событий.

**НАХОДКИ из материалов кейса:** [Payson](https://doi.org/10.1016/j.spacepol.2026.101762) помогает отделить общественный конечный результат от частных промежуточных услуг; [Zancan et al.](https://doi.org/10.1016/j.spacepol.2025.101735) связывают закупку с готовностью, спросом и критичностью; [Takata/Hidaka](https://doi.org/10.1016/j.actaastro.2025.02.009) — с взаимодействием и компетенциями сторон; [Melamed et al.](https://doi.org/10.1016/j.spacepol.2024.101626) — с рисками зависимости и расхождения целей. [OECD](https://doi.org/10.1787/cbf9b240-en) указывает на роль якорного спроса и ограничения повторяемости коммерческого спроса. Ни одна из этих работ не подтверждает наши будущие доходы, скидки или коэффициенты D. Подробное чтение — [case-literature.md](research/case-literature.md).

## Собственный режим D

**ГИПОТЕЗА:** общественный базовый результат плюс платные дополнительные услуги может быть отдельным режимом. Должны быть описаны получатели, сроки и объём бесплатного результата, платный продукт, лицензионные права, дополнительные затраты и чистый прирост спроса с учётом вытеснения прежних продаж. [Границы подтверждения режимов литературой](research/case-literature.md).

В принятом алгоритме перечисляются A/B/C. Исследовательские коэффициенты D не переведены в производственные входы: для них пока нет подтверждённой сметы и спроса. Ранее рассчитанные D-варианты остаются условными сценариями. При подтверждении D его следует включать в общее пространство по тому же правилу Q и явно обновить версию входов/шкал; добавление D не гарантирует, что алгоритм его выберет.

VPUB не складывается с CASH. STRESS меняет официальный лимит запуска и не заменяет проверку спроса, цен, доступности поставщика или времени поступления денег.

### Файлы и единицы

- `portfolio_detail.csv` — выбранные лоты после применения режимов;
  `portfolio_metrics.json` — суммы и средние портфеля.
- `team_decision_config.json` — состав, параметры и допущения; `export_provenance` хранит хеши,
  `document_values` — слепок чисел для сверки документов.
- `hybrid_analysis.json` — результат выбора и шесть оценок. `checks.BASE` / `checks.STRESS` —
  проверки одного состава; `headroom` — пределы изменения входов по отдельности;
  `search_summary` — итоги перебора; `alternatives`, `switching_curve`, `sensitivity` — компактные сравнения.
  Полная таблица сочетаний и отдельные CSV проверок больше не генерируются: в `results/` четыре файла.
- `lots.csv` — исходные лоты; `access_modes.csv` — множители A/B/C.
- `mrub` — млн ₽; `mrub_per_year` — млн ₽/год; `_1_5` — шкала индекса 1–5;
  `pct` — проценты; `factor` / `multiplier` — множитель.
- `true` / `false` — да / нет; `null` или пустая ячейка — отсутствует либо неприменимо, не обязательно ноль.
  Десятичная точка в CSV означает то же, что запятая в тексте: `305.75` = 305,75.

### Лоты и режимы

- `lot_id` — код лота; `service` — его описание. FIRE — пожары; FLOOD — паводки;
  AGRI — агроаналитика; INFRA — деформации инфраструктуры; ARCTIC — удалённая логистика;
  TRANS — транспорт; ENV — экология; SSA — космическая обстановка.
- `territorial_archetype` — класс территории лота; `territorial_archetypes` — число
  учитываемых классов портфеля. `federal=true` исключает лот из этого счётчика.
- `capability_groups` — группы возможностей лота, а в сводной метрике — их количество;
  `capability_set` — список. EO — наблюдение Земли; PNT — положение, навигация и время;
  InSAR — радиолокационная интерферометрия; SATCOM — спутниковая связь;
  SSA — осведомлённость о космической обстановке. PNT/InSAR считается одной группой кейса.
- `lots` и `modes` — соответствующие строки состава и режимов: FIRE+AGRI+TRANS+ENV
  с ABBA означает FIRE:A, AGRI:B, TRANS:B, ENV:A. `selection` — пары «лот — режим»;
  `selection_id` — их стабильная запись; `selected_lots` — число выбранных лотов.
- `mode_id` — A/B/C, не английские аббревиатуры; `public_core` — флаг общественного ядра,
  `public_core_lots` — число таких лотов. Флаг не заменяет договорные права пользователей.
- `k_c0`, `k_opex`, `k_vpub` — множители соответствующих исходных величин;
  `k_anchor`, `k_commercial` — множители якорных и коммерческих поступлений.
  Например, 1,05 означает +5%, 0,25 — сохранение четверти исходного значения, не долю пользователей.

### Экономика и индексы

- `C0` / `c0` / `c0_mrub` — затраты запуска, млн ₽ единовременно.
- `OPEX` / `opex` / `opex_mrub_per_year` — расходы эксплуатации за год.
- `CASH` / `cash` / `cash_mrub_per_year` — поступления за год;
  `anchor_cash_mrub_per_year` и `commercial_cash_mrub_per_year` — их якорная и коммерческая части.
- `VPUB` / `vpub` / `vpub_mrub_per_year` — общественная ценность по синтетической шкале кейса;
  это не поступление на счёт оператора и не слагаемое CASH.
- `KCASH` / `kcash` = CASH / OPEX — доля покрытия расходов; 1 — равенство поступлений и расходов.
- `S` / `surplus` / `annual_surplus_mrub` = CASH − OPEX — годовой остаток,
  без возврата C0, налогов и стоимости капитала; это не прибыль.
- `readiness` / `readiness_1_5` — готовность, не шкала TRL 1–9;
  `resilience` / `resilience_1_5` — устойчивость, не вероятность успеха;
  `scale` / `scale_1_5` — тиражируемость. Для портфеля берётся среднее по лотам.
- `t_rep` — отдельный безразмерный показатель; проверяется среднее портфеля.
  Его методология не раскрыта; не подменяем им `scale`.

### Проверки и запас

- `code` / `title` — код и название условия; `operator` — знак сравнения;
  `threshold` / `actual` / `unit` — порог, факт, единица; `status` — PASS или FAIL.
- `slack` — запас: для верхнего порога `threshold − actual`, для нижнего `actual − threshold`.
  Отрицательный запас — нарушение. Для равенства успешная проверка даёт 0,
  неуспешная — пустое значение; канон использует технический допуск 1e-9.
- `BASE_ok` / `STRESS_ok` — все проверки сценария; `chk_…` — отдельная проверка BASE.
  Девять кодов: `exact_lot_count`, `territorial_archetypes`, `capability_groups`,
  `public_core_lots`, `c0_limit`, `opex_limit`, `vpub_floor`, `kcash_floor`, `t_rep_floor`.
- В анализе запаса `input` — изменяемый вход, `direction` — рост или падение,
  `limit_factor` — предельный множитель, `change_pct` — изменение в процентах,
  `binding_constraint` — достигаемый порог. Порог нулевого S — условие команды,
  отдельно от официального KCASH; пределы разных шоков не применяются одновременно.
- `cash_drop_break_even_pct` / `opex_growth_break_even_pct` — падение поступлений
  или рост расходов до S = 0 при прочих неизменных.

### Поля выбора

- `raw` — значение до нормирования; `z` / `normalized` — оценка;
  `minimum` / `maximum` / `bounds` — границы шкал.
- `key` / `title` / `direction` в компоненте Q — код, название, направление предпочтения;
  здесь `max` — больше лучше, `min` — меньше лучше.
- `Q` / `q` — минимум шести оценок; `q_exact` — точная дробь;
  `bottleneck` — критерий, определяющий минимум; `q_max` — лучший Q после денежного отсечения.
- `Smax` / `s_max_mrub` — максимальный S после дополнительных требований, до Δ;
  `cash_loss_limit_mrub` — заданный Δ, `effective_delta_mrub` — применённый Δ;
  `cash_floor_mrub` = Smax − Δ ограничивает S, несмотря на название поля.
- `quality_epsilon` — ε, в текущей версии 0; `reference_count` — число вариантов для шкал;
  `feasible_count` — после условий поиска; `cash_eligible_count` — после Δ.
- `max_q_count` — число вариантов с лучшим Q в области поиска: до денежного
  разрешения равенства при авто Δ, после денежного ограничения при ручном Δ.
- `winner` — результат выбора; `switching_curve` — интервалы неизменного победителя:
  `delta_from_mrub` включён, `delta_to_exclusive_mrub` исключён; `null` сверху — без конечной границы.
- `sensitivity` — дополнительные сценарии; `winner_changed` — изменился ли победитель;
  `original_still_feasible` — допустим ли прежний до Δ;
  `original_adjusted_surplus_mrub` — его S после шока.
- `dataset_hash` — версия данных; `input_hash` — входы запроса с версией движка;
  `engine_version` — версия реализации.

### Воспроизведение пользовательских сценариев

**ФАКТ реализации:** сохранённый вариант содержит собственный снимок лотов и режимов
`inputs`. Сравнение использует входы каждого варианта; одинаковый состав с разными
ценами не объединяется. Команда `evaluate --snapshot team_decision_config.json`
повторяет скачанный расчёт без нового подбора. В обычном CLI все команды используют
`algorithm_parameters.inputs`. Официальные файлы остаются неизменными.
Управленческие поля эксперимента помечаются `reference_requires_review`: численный
пересчёт сам по себе не подтверждает прежнюю схему договоров и финансирования.
Источники реализации: [CLI](../backend/app/core/services/portfolio_engine/cli.py),
[экспорт UI](../frontend/src/entities/portfolio/lib/snapshot.ts).
