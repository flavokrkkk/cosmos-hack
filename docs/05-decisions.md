## 11.09.2026 — публичный портфельный API для прототипа

**ФАКТ — решение пользователя и [реализация](../backend/app/api/v1/routers/portfolio.py):**
catalog/evaluate/recommend/compare доступны без входа. Административная авторизация сохранена.
Причина — общий каталог и отсутствие личных серверных данных; логин мешает демонстрации.
Альтернатива — обязательные аккаунты и хранение решений в PostgreSQL — отложена для прототипа.
**Статус:** API открыт; frontend не изменён, браузерное сохранение ещё не реализовано.

**ГИПОТЕЗА реализации черновиков:** localStorage вместо cookies: хранить версию схемы,
dataset_hash, selection и настройки, не доверять сохранённым метрикам. При восстановлении
проверять актуальный каталог и пересчитывать на backend; при несовпадении dataset_hash
просить подтвердить перенос выбора на новые данные. Проверка — восстановление после
перезагрузки, обработка повреждённого/устаревшего JSON и недоступного хранилища.
Это локальное удобство одного браузера, не общая БД и не резервная копия; для переноса
позже нужен экспорт/импорт. До публичного размещения проверить ограничения частоты запросов.

## 12.09.2026 — кейсовый сценарий без PostgreSQL, Redis и очереди

**ФАКТ — решение пользователя и [реализация](../backend/app/api/v1/routers/portfolio.py):**
расчёты, автоподбор, сравнение и объяснение не сохраняются на сервере. `POST /portfolio/explain`
повторяет расчёт, вызывает Ollama и возвращает результат в одном HTTP-ответе. PostgreSQL,
Redis, Taskiq, `job_id`, polling и авторизация для портфельных маршрутов не используются.

Причина — однопользовательский демонстрационный прототип не требует общей истории,
совместного редактирования и фоновой обработки; расчёт короткий, а локальная генерация
укладывается в ограниченный запрос с шаблонным fallback. Черновики планируется хранить
в `localStorage`, переносить через экспорт/импорт и всегда пересчитывать на backend.

Альтернатива — таблица заданий в PostgreSQL и очередь Redis/Taskiq — удалена из кейсовой
логики как лишняя сложность. Общая инфраструктура каркаса сохранена для административных
маршрутов и возможного будущего многопользовательского режима. **Статус:** backend реализован
и проверен реальным вызовом Ollama; браузерное сохранение ещё не реализовано.

## 12.09.2026 — frontend собран заново под дизайн-систему макетов

**ФАКТ — решение пользователя (Egor) и реализация ([frontend README](../frontend/README.md),
[заметка](notes/2026-09-12-frontend-design-system.md)):** одна страница с двумя режимами
«Автоподбор / Ручная проверка» по предоставленным макетам; бренд `#0091FF`, мягкие карточки,
«веер» рекомендованных лотов, модалка «Подробнее о лоте», блок «Почему такой выбор?».

- **Стек UI:** Tailwind CSS v4 (токены дизайн-системы в `@theme`) + примитивы Radix
  (`radix-ui`: Dialog, Switch, Tooltip, ToggleGroup, Collapsible) + `class-variance-authority`
  — подход shadcn, но компоненты написаны под нашу систему в `shared/ui`, а не скопированы.
  Иконки — `lucide-react`, шрифт — самохостинг Inter (без внешних CDN: эксперт может быть офлайн).
  Альтернатива — готовые shadcn-компоненты с их темой — отклонена: макет не совпадает с их
  геометрией, переписывать пришлось бы всё равно.
- **Сохранение «в рамках сессии»:** рабочее состояние страницы (режим, сценарий просмотра,
  условие STRESS, выбранные вручную лоты, открытый вариант) — Zustand `persist` в
  `sessionStorage`; результаты расчётов — кеш React Query, персистируемый в `sessionStorage`
  (`@tanstack/react-query-persist-client`). Хранятся только входы; все ключи включают
  `dataset_hash`, при смене версии данных состояние сбрасывается. «Сохранить вариант» —
  отдельный список в `localStorage` (входы + версии, показатели пересчитываются при открытии).
  Cookies и серверное хранение не используются — согласуется с записью от 11.09.
- **Семантика результата после правки бэкенда 12.09:** интерфейс не называет ничего
  «рекомендацией алгоритма». Сверху — **«Портфель команды»** (если он лежит на фронте области
  поиска), ниже — **опорные точки фронта** с подписью «границы возможного, а не то, что
  следует выбрать». Если портфеля команды на фронте нет (другие условия или другие четыре лота),
  по умолчанию открыта первая опорная точка и это сказано словами.
- **Ручная проверка — по плану §14:** пользователь выбирает четыре лота, режимы подбирает
  сервер (`recommend` с `lot_ids`) сразу после четвёртого лота. При 1–3 лотах денег нет
  (на макете цифры при «1 из 4» — заглушка дизайнера), но показан прогресс по условиям, не
  зависящим от режима: лоты, территориальные архетипы, группы возможностей — «набрано / пока
  не набрано». Альтернатива — полный предварительный расчёт с режимом A — отклонена: числа
  менялись бы после назначения режимов сервером, а недобор по минимумам читался бы как
  нарушение.
- **Объяснение:** один синхронный `POST /portfolio/explain` по кнопке; факт запроса и
  результат живут в сессии, шаблонный fallback помечается «модель недоступна».

**Статус:** реализовано, `npm run lint` и `npm run build` зелёные, сценарии автоподбора,
ручной проверки, сравнения, сохранения, экспорта и объяснения проверены в браузере на живом
бэкенде 12.09. Не реализовано: обоснование/план реализации (R1), «принять основным» (S1),
четыре усиления (U1–U4) — остаются в плане.

## 12.09.2026 — подбор в два шага: числа сразу, объяснение вторым запросом

**ФАКТ — замер и реализация ([заметка](notes/2026-09-12-frontend-design-system.md)):**
после переноса объяснений внутрь `recommend` первый вызов на этой машине занимал 74,7 с и
возвращал шаблон (Ollama в Docker на CPU не укладывается в таймаут пакета). Добавлен флаг
`with_explanations` в `RecommendRequest` (по умолчанию `true`, `input_hash` не меняется);
фронтенд вызывает ручку дважды — без объяснений для чисел (доли секунды) и с объяснениями
для блока «Почему такой выбор?». Причина — правило брифа AI1: ошибка или медленная модель не
должна блокировать подбор, сравнение, сохранение и экспорт. Альтернатива — ждать пакет в одном
запросе — отклонена: минута без чисел на защите неприемлема. **Статус:** реализовано, 64 теста
бэкенда зелёные; на защите нужна нативная Ollama с GPU или короче пакет, иначе объяснение — шаблон.

## 11.09.2026 — все четыре алгоритмических усиления включены в план

**ФАКТ — решение команды по запросу «обнови план» после обсуждения четырёх усилений:**
целевой объём включает выбор с учётом запаса прочности, дополнительные стресс-сценарии,
чувствительность рекомендации и поиск с закреплениями/исключениями. Причина — объяснять
не только победителя, но устойчивость выбора, границы применимости и цену условий пользователя.
Альтернатива — ограничиться Парето и лексикографическим выбором одного варианта.
**Статус: принято в план, не реализовано этой правкой.** Подробности и приёмка —
[план §4.4–4.7, §10–12](08-backend-frontend-plan.md), UX — [бриф U1–U4](09-designer-brief.md).

**ГИПОТЕЗА формализации:** `robust_epsilon_v1` выбирает максимальный худший нормированный
запас при явном допуске по общественному эффекту. Проверка — ручные примеры, полный перебор,
граничные тесты и воспроизводимость. Ненулевой допуск и факторы сценариев требуют основания;
они не являются официальными данными. Канонические формулы и BASE/STRESS не меняются.

Уточняет прежние записи о выдаче только Парето-множества и об аналитической устойчивости:
Парето и аналитический headroom сохраняются, но не заменяют подбор одной рекомендации
и повтор полного поиска для определения её смены. MCDA/D — после этих четырёх усилений;
Ollama-пояснение уже реализовано отдельно и не заменяет незавершённый P1.
