## 2. Итоговый пользовательский сценарий

**ГИПОТЕЗА UX; проверка — сквозной тест §12:**

1. Пользователь входит штатным способом; для эксперта команда заранее выдаёт демодоступ.
2. Приложение автоматически получает все восемь лотов, A/B/C, ограничения и версию данных.
   В первой версии не нужен произвольный CSV-upload или ручное подтверждение каждой карточки.
3. Пользователь видит правило выбора и область поиска: BASE или варианты, проходящие
   также STRESS. Выбирает базовый метод или устойчивый подбор; во втором случае видит
   допустимую уступку по эффекту и набор дополнительных сценариев. Нажимает «Подобрать портфель».
4. Приложение показывает рекомендуемые четыре лота с режимами, показатели, девять проверок,
   объяснение метода, число рассмотренных/допустимых вариантов и несколько альтернатив.
5. «Изменить вручную» создаёт копию рекомендации. Замена лота/режима вызывает новый расчёт;
   исходный вариант сохраняется для сравнения.
6. Просмотр BASE/STRESS проверяет один и тот же состав. «Подобрать для других условий» —
   отдельное действие, не скрытая замена состава при переключении сценария.
   В раскрываемом блоке проверяет дополнительные сценарии и границы смены рекомендации.
   Может закрепить/исключить лоты или режимы и повторить поиск, увидев цену этих условий.
7. Команда сравнивает варианты, заполняет обоснование и явно принимает основной портфель.
   «Рекомендован алгоритмом», «сохранён» и «принят командой» — разные статусы.
8. Раскрывает подробности выбранного варианта, сравнение и обоснование на этой же странице,
   не теряя текущий выбор; экспортирует проверяемый снимок решения и материалы для записки.
9. По желанию нажимает «Объяснить»: Ollama оформляет факты из актуального расчёта.
10. Внизу страницы открывает «Материалы решения»: GitVerse, записку, стресс-резюме,
    презентацию, исходные данные, конфигурацию, контрольные результаты и инструкции проверки.
    Пакет сдачи относится к зафиксированному решению команды, не к случайному текущему draft.

**ГИПОТЕЗА приоритетов:**

- **P0, обязательный продуктовый путь:** официальный каталог, канонический evaluate,
  алгоритмическая рекомендация, альтернативы, ручной fork, BASE/STRESS, диагностика,

- **P1, согласованное алгоритмическое усиление — все четыре обязательны для целевого плана:**
  запас прочности влияет на выбор; дополнительные сценарии; границы допустимости и смены
  рекомендации; поиск с закреплениями/исключениями и объяснение цены условий. P0 — промежуточная
  рабочая версия, без P1 расширенный план не считается завершённым.
- **P2, после P0/P1:** Ollama «Объяснить решение», MCDA как ещё один метод, пользовательский D,
  свободные вопросы с ограниченным набором операций, улучшенное оформление отчёта.

Не входят в первую версию: разработка самих космических сервисов, новые датасеты,
ML/обучение, отдельный расчётный микросервис, универсальная договорная система,
реальные интеграции плательщиков, карты ради оформления, NPV/многолетние потоки,
Монте-Карло, перезапись официальных цен, WebSocket/SSE и новая авторизация. Дополнительные
сценарии меняют только отдельные расчётные копии входов с явной маркировкой допущений.

## 4. Алгоритм автоматического подбора

### 4.1. Каноническая часть

**ФАКТ — CSV/config и engine:** пространство стандартных комбинаций — C(8,4) × 3⁴ = 5670.
Каждый вариант — четыре уникальных лота, у каждого свой mode_id. Результаты организаторов:
C0, OPEX, VPUB и CASH суммируются, KCASH = суммарный CASH / суммарный OPEX, индексы
усредняются. SSA не увеличивает число территориальных архетипов, PNT/InSAR — одна группа.
BASE/STRESS отличаются только лимитом C0. VPUB не является денежным поступлением.

**ГИПОТЕЗА реализации:**

- [ ] Использовать все лоты из выбранной версии набора, не предварительно выбранные четыре.
- [ ] Рассчитать все пары лот/режим и все комбинации; переиспользовать существующий перебор.
- [ ] Проверить все девять условий каждого сценария, не заменять фильтрацию штрафом в score.
- [ ] Возвращать размер пространства, counts BASE/STRESS/Парето и параметры фильтра.
- [ ] Если допустимых нет, вернуть `status: no_feasible`, причины и `recommended: null`.
  Не ослаблять условия и не объявлять «наименее плохой» вариант допустимым.
- [ ] Проверки и ранжирование используют неокруглённые значения. Нынешнее округление
  в `engine/space.py:metrics_row` оставить только для отображения/старого CSV либо убрать
  из рабочего расчётного представления с регрессионной проверкой.

### 4.2. Базовый метод для сравнения

**ГИПОТЕЗА стартового метода: `pareto_lexicographic_v1`.** Он развивает Парето из
[07-action-plan.md](07-action-plan.md) и не требует придумывать неутверждённые веса.
Проверка: ручные примеры, перестановка входных строк и сверка максимума по первому приоритету.

1. Оставить допустимые варианты в явно выбранной области.
2. Построить Парето по объявленным критериям и направлениям существующего engine:
   максимизируем VPUB, KCASH, t_rep, readiness, resilience, scale; минимизируем C0/OPEX.
3. Применить **явно упорядоченный список приоритетов**. Предлагаемый начальный профиль:
   VPUB больше → C0 меньше → OPEX меньше → KCASH больше → t_rep/readiness/resilience/scale
   больше → стабильный ID варианта. Показать этот порядок до запуска.
4. Второй критерий используется только при равенстве первого, третий — при равенстве
   предыдущих. Это не «баланс»: профиль назвать **«Общественный эффект в заданных условиях»**.
5. В первой версии сравнивать исходные неокруглённые показатели после детерминированного
   порядка суммирования лотов; допуск 1e-9 относится к каноническим ограничениям, не к
   скрытому объединению разных score. При точном равенстве всех критериев сортировать
   по стабильному ID. Это разрешает техническую ничью, а не доказывает превосходство.
6. Возвращать несколько альтернатив: следующие по тому же правилу и представители
   иных компромиссов, например меньший C0 или больший KCASH. Подписывать основание каждого.
7. Объяснение строить из фактов: первый различающий критерий, дельты, запасы и нарушения.
   Не приписывать алгоритму оценку договоров или рисков, которых нет в его входах.

**ГИПОТЕЗА политики:** первоначально `require_stress=true`, как предложено в 07: это наша
стратегия, не обязательное правило кейса. Пользователь может отдельно выполнить поиск
с `require_stress=false` в BASE и увидеть цену стресс-устойчивости. Не исключать BASE-only
варианты из каталога или ручного сравнения. Окончательные приоритеты команда утверждает
до фиксации конкурсного решения; профиль нельзя подгонять незаметно под пример из config.

Этот метод остаётся доступным как контрольный baseline. Он **не учитывает запас прочности
в выборе**: показывать запас рядом с результатом недостаточно. Целевой усиленный метод — §4.4.

### 4.3. Что именно означает «чувствительность»

**ФАКТ — [engine/sensitivity.py](../engine/sensitivity.py):** текущий модуль считает запас
до нарушения ограничений, а не изменение победителя при других предпочтениях.

**ГИПОТЕЗА реализации:** разделить две функции:

- **Запас допустимости:** сколько остаётся до порога; существующий headroom адаптировать.
  Если портфель уже недопустим, показывать дефицит, а не положительный «запас устойчивости».
- **Устойчивость выбора:** повторить весь подбор при изменении входного параметра,
  допуска по эффекту, набора сценариев, приоритетов или require_stress; найти участки,
  на которых меняется победитель, см. §4.6. Это не ±20% весов: у текущих методов весов нет.

Если добавляем **MCDA**, отдельно реализовать направления, нормировку с зафиксированной
базой и обработкой постоянного критерия, неотрицательные нормированные веса и их источник,
разложение score, ничьи и пересчёт при ±20% с явным правилом перенормировки. Нормировочную
базу не менять между сравниваемыми прогонами чувствительности. Не добавлять пункт MCDA
в UI, пока за ним нет алгоритма и тестов. Это расширение, не блокер первой рекомендации.

### 4.4. Усиление 1 — выбор с учётом запаса прочности

**ГИПОТЕЗА метода `robust_epsilon_v1`:** максимизируем худший нормированный запас среди
вариантов с приемлемой уступкой по общественному эффекту. Это наше правило решения,
не новая официальная метрика. Проверка — ручные примеры и полный перебор по §11.

1. Из полного пространства получить множество F: все официально допустимые варианты
   в выбранной области BASE/require_stress, с учётом явных условий пользователя (§4.7).
   Если F пусто — `no_feasible`. Вычислить `V* = max(VPUB_BASE)` по F и контрольный
   вариант методом §4.2. Дополнительные сценарии пока не отсекают варианты из F.
2. Пользователь задаёт `epsilon` — максимальную относительную уступку по VPUB:
   оставить `VPUB_BASE >= (1 - epsilon) * V*`, где `0 <= epsilon <= 1`.
   При `epsilon=0` общественным эффектом не жертвуем. Не зашивать необоснованный
   ненулевой допуск: первоначально 0, иной выбор явно подтвердить и сохранить с основанием.
3. Для каждого оставшегося варианта рассчитать все сценарии §4.5 и девять проверок.
   Для рекомендации требовать прохождение всех выбранных сценариев; недопустимые
   сохранять в диагностике. Отсутствие такого варианта — `no_robust_feasible`:
   официально допустимые варианты существуют, но условия устойчивости не выполнены.
   Вернуть baseline и причины отдельно, не объявлять его устойчивой рекомендацией и
   не увеличивать epsilon/бюджет автоматически.
4. Считать нормированный запас по непрерывным ограничениям C0, OPEX, VPUB, KCASH, t_rep:
   для верхнего порога `m = (limit - actual) / limit`, для нижнего
   `m = (actual - limit) / limit`. Все эти пороги в текущем наборе положительны;
   неподдерживаемый нулевой/отрицательный порог валидировать, не делить на ноль.
   `R(p) = min(m(p, scenario, constraint))` по всем выбранным сценариям и этим пяти
   ограничениям. Хранить signed margin; отрицательное значение — дефицит. Канонический
   допуск при проверке не округляет R и не превращает дефицит в положительный запас.
5. Выбрать максимальный R; при точном равенстве применить порядок §4.2 и стабильный ID.
   Дискретные условия (4 лота, архетипы, группы, public_core) остаются жёсткими проверками,
   но не входят в минимум R: обязательные 4/4 иначе дали бы всем нулевой запас.
6. Вернуть уступку по VPUB относительно V*, изменение R, худшие сценарий/ограничение,
   дельты к baseline, epsilon и основание настройки. Отдельно показать вариант с
   максимальным эффектом и другие реальные компромиссы без дублирования одного состава/режимов.

**Ограничения метода:** R — консервативная оценка близости к порогам, не вероятность успеха
и не процент допустимого одновременного ухудшения всех входов. Нормировка по порогу и выбор
минимума — наши допущения; они могут делать один неизменяемый индекс решающим. В UI и отчёте
показывать ограничение, определившее минимум, и чувствительность к epsilon/сценариям.
Не обещать, что этот профиль обязательно сменит победителя или даст лучший конкурсный балл.

**Важно для реализации:** не отбрасывать кандидатов устойчивого метода по старому Парето
из §4.2 до расчёта R: агрегаты BASE могут скрывать различную реакцию на сценарий. На текущем
малом пространстве выбирать по всем кандидатам. Парето остаётся средством объяснения;
если вводится предварительное отсечение, сначала доказать его корректность для нового метода.

### 4.5. Усиление 2 — дополнительные стресс-сценарии

**ГИПОТЕЗА модели сценария; проверка — неизменность канона, ручные расчёты и воспроизведение:**

- BASE/STRESS организаторов неизменны. Добавить отдельные сценарии команды: рост C0,
  рост OPEX, снижение якорных/коммерческих поступлений и сочетание таких изменений.
  VPUB при необходимости изменяется отдельным явно заданным фактором, не вместе с CASH.
- `ScenarioDefinition` содержит ID/version, родительский BASE или STRESS, точные множители,
  область воздействия (все лоты или перечисленные ID/группы), источник `допущение`, основание.
  При пересечении групп применить фактор один раз; в v1 запрещать неоднозначные перекрывающиеся
  правила для одного поля/лота. Коэффициенты конечные и неотрицательные; OPEX должен оставаться
  положительным. Пределы UI/API согласовать и описать как наши технические границы.
- Применять факторы к копии исходных полей лота, затем канонические A/B/C и агрегирование;
  KCASH каждый раз пересчитывать из CASH/OPEX. Не умножать KCASH независимо, не менять
  коэффициенты режимов и официальные ограничения. Фактор бюджета вне BASE/STRESS возможен
  только в явно обозначенной диагностике чувствительности, не как правка официального STRESS.
- В выбранный набор анализа всегда включать BASE и STRESS при require_stress; дополнительные
  сценарии применять к тому же составу/режимам. Для устойчивого метода они являются
  условиями прохождения; для просмотра ручного/baseline-варианта — диагностикой, не сменой выбора.
- Никакие ненулевые проценты ухудшений не считаются заданными кейсодержателем. Команда
  фиксирует значения и основания до финального выбора, пользователь видит их до запуска.
  При отсутствии дополнительных сценариев честно писать «проверены только BASE/STRESS».
- Вернуть по каждому сценарию totals/checks, дельты, запас/дефицит и причину отказа.
  Доля пройденных сценариев — описательная статистика выбранного набора, **не вероятность**.
  Вероятностные распределения/Монте-Карло не нужны для этих четырёх усилений.

### 4.6. Усиление 3 — чувствительность рекомендации

**ГИПОТЕЗА двух отдельных результатов; проверка — повторный перебор в контрольных точках:**

- **Граница допустимости фиксированного портфеля.** Использовать аналитический headroom
  там, где его формула применима: один параметр меняется, остальные зафиксированы.
  Указывать сценарий и условие, которое нарушается первым. Не переносить однопараметрическую
  формулу на совместное ухудшение или произвольное подмножество лотов без проверки.
- **Граница изменения рекомендации.** На ограниченной сетке одного параметра (например,
  рост OPEX, падение поступлений, бюджет диагностической копии или epsilon) повторить весь
  алгоритм по всем кандидатам с теми же пользовательскими условиями. В каждой точке заново
  вычислять допустимость, V*, эффектный допуск и R. Нельзя проверять только прежний топ-N.
- Возвращать интервалы/точки с победителем, первый наблюдаемый переход, дельты и причину:
  старый вариант нарушил ограничения либо остался допустим, но проиграл по правилу выбора.
  Сохранять также участки без решения. Переключение A → B → A допустимо: победитель не обязан
  меняться монотонно. Не искать единственную «точную границу» слепым бинарным поиском.
- Результат сеточного анализа подписывать «на проверенной сетке» с шагом и диапазоном;
  переход между точками — интервал, не доказанный точный порог. Дополнительное уточнение
  разрешено с явной точностью, без обещания отсутствия других переходов внутри шага.
- Отдельные дискретные прогоны могут сравнивать require_stress, набор сценариев или порядок
  приоритетов. Не смешивать несколько изменений в одной причинной интерпретации.
- Установить лимиты количества точек/сценариев, кешировать по всем входам, измерить время.
  Если рекомендуемый вариант не изменился, вернуть диапазон проверки, а не обещание вечной устойчивости.

### 4.7. Усиление 4 — поиск альтернатив с условиями пользователя

**ГИПОТЕЗА запроса `SearchConstraints`; проверка — исчерпывающая сверка найденных кандидатов:**

- `required_lot_ids`, `excluded_lot_ids`; `fixed_modes` закрепляет режим и одновременно
  включает соответствующий лот. Неизвестные ID/режимы, пересечение include/exclude,
  более четырёх обязательных лотов и противоречивые закрепления — 422 до поиска.
- Опционально `reference_selection` и `max_lot_replacements`: число замен равно
  `4 - |reference_lots ∩ candidate_lots|`. Смена режима не считается заменой лота;
  отдельный `max_mode_changes` ограничивает изменения режимов только у общих лотов.
  В UI эти два условия подписать раздельно; reference — полный валидный по структуре портфель.
- Фильтровать пространство до выбора победителя, затем выполнять тот же базовый/устойчивый
  метод со всеми официальными условиями. Закрепление не отменяет бюджет и public_core.
- Вернуть лучшую найденную альтернативу, её состав/режимы, отличия и дельты к поиску без
  пользовательских ограничений при том же методе/сценариях/epsilon. V* считается отдельно
  в каждом поиске и оба значения показываются: одинаковый epsilon не означает общий абсолютный
  минимум VPUB. Дельты называть ценой/выигрышем условий, не обещать ухудшения каждой метрики.
- Если безусловный подбор тоже не дал рекомендации, сравнение с ним недоступно с объяснением.
  Сохранять дополнительно выбранный пользователем reference для сравнения, не подменять им
  алгоритмический контрольный результат.
- При `no_feasible`/`no_robust_feasible` показать влияние фильтров и при необходимости
  проверенные повторным поиском варианты снятия одного условия. Не выдавать предположение
  о конфликте за доказательство и не обещать минимальный конфликт без отдельного алгоритма.

**Итоговый конвейер:** канонические расчёты → официальная допустимость и условия пользователя →
допуск потери эффекта → дополнительные сценарии → выбор по худшему запасу → альтернативы →
чувствительность. Последний шаг анализирует рекомендацию, а не скрытно меняет её. Все четыре
усиления сохраняются в одном воспроизводимом снимке; Ollama для них не требуется.

### B2. DTO и состояния

**ГИПОТЕЗА контрактов; точные схемы зафиксировать в OpenAPI до параллельной разработки UI:**

- `CaseCatalog`: dataset_id/version/hash, source refs, восемь лотов, A/B/C, BASE/STRESS,
  units, происхождение значений, перечень поддерживаемых методов и допустимых настроек.
- `SelectionItem`: `lot_id`, `mode_id`. Полный портфель — ровно четыре уникальных ID.
  Для ручного черновика API может принимать 0–4: пустой возвращает `incomplete` без
  NaN-метрик; 1–3 рассчитываются как неполные. Более четырёх, дубликаты и неизвестные ID — 422.
- `Calculation`: canonical input/hash, engine_version, per-lot detail, totals,
  checks отдельно для BASE/STRESS, `feasible_by_scenario`, годовой непокрытый OPEX.
- `ConstraintCheck`: code/title/operator/threshold/actual/unit/slack/passed/message.
  Допуск сравнений как в каноне; сериализация в стандартные JSON-типы без NaN/Infinity.
- `RecommendationRequest`: dataset_hash, method_id/version, ordered priorities,
  scenario, require_stress, epsilon, versioned scenario definitions и SearchConstraints;
  четыре выбранных лота не являются обязательным входом (кроме reference для ограничения замен).
- `RecommendationResult`: request/input hash, параметры поиска, counts, рекомендованный
  вариант или null, alternatives, доказуемые причины, версия правила ничьих;
  `status=ok|no_feasible|no_robust_feasible`, baseline, V*, effect_loss, R,
  worst_scenario/constraint, counts после каждого фильтра и результаты сценариев.
- `ScenarioDefinition` и `ScenarioEvaluation`: происхождение/основание факторов, родительский
  сценарий, область воздействия, исходный input hash, transformed input hash, totals/checks.
- `SearchConstraints`: закрепления/исключения, reference и раздельные ограничения замен лотов
  и режимов. В результате — сравнение с безусловным подбором, оба V*, проверенные причины отказа.
- `SensitivityRequest/Result`: snapshot, анализируемый параметр, область воздействия,
  диапазон/шаг/точность, точки с победителями/статусами, интервалы переходов и отдельные
  границы допустимости. Все настройки входят в input hash; backend задаёт лимиты нагрузки.
- `Decision`: имя, версия, recommendation snapshot, варианты, chosen_variant_id,
  обоснование, источники/допущения, stress decision, происхождение ручных копий.
  `origin=algorithm|manual|imported|example` не смешивать со статусом принятия.
- `DecisionRationale`: per-lot потребность/роли/доступ/финансирование/закупка/риски/
  переносимость/этапы/KPI; portfolio-level стратегия, компромиссы и ответ на стресс.
- `SubmissionManifest`: submission_version, pinned repository URL/commit,
  published_decision_id/revision, dataset_hash, engine_version, инструкция запуска/проверки,
  разрешённые к выдаче материалы. У материала: id/category/title/description/status,
  формат, размер/хеш для локального файла, download endpoint или разрешённая внешняя ссылка.
  Статусы `draft|ready|unavailable` не подменяют факт наличия файла или проверки ссылки.
- Статусы считать отдельно: `input_status`, `calculation_status`, `rationale_status`,
  `decision_status`. Непустое поле с `TODO` не считать законченным обоснованием.

**ГИПОТЕЗА единственного источника данных UI:** каталог, режимы, финансовые значения,
счётчики, ограничения, рекомендации, сравнения, сохранённые обоснования и manifest приходят
с backend. Frontend хранит draft формы и состояние раскрытия блоков, форматирует ответ,
но не повторяет формулы или официальные пороги. Панель метрик, список проверок и детали
используют один `Calculation` и input hash. Текст об операторе/плательщике вводит команда,
backend его хранит, а не извлекает несуществующие сведения из CSV. Фикстуры разрешены
в тестах/разработке с явной маркировкой, но не как fallback живого результата.

Фоновая задача допустима только при подтверждённой длительности, а не по умолчанию для 5670 строк.

### B4. Хранение решений

**ГИПОТЕЗА минимальной модели PostgreSQL:** таблица `portfolio_decisions` с `id`,
`owner_admin_id`, `name`, `revision`, `schema_version`, `dataset_hash`, `engine_version`,
`payload JSONB`, временными метками. История снимков — отдельная таблица или immutable revisions.
JSONB принимает только валидированную DTO, а не произвольный клиентский объект.

- [ ] Alembic-миграция, SQLAlchemy models в infrastructure, repository в core/repositories.
- [ ] Роуты вызывают сервисы; операции SQL только через repository.
- [ ] Сохранение не доверяет клиентским metrics/score: сервер считает сам и связывает
  snapshot с input hash. Изменение входов делает прошлые объяснения неактуальными.
- [ ] Оптимистическая версия: при устаревшем revision вернуть 409, не затереть чужую правку.
- [ ] Сервер разрешает принятие основным только свежего, пересчитанного полного варианта
  из четырёх уникальных лотов, проходящего BASE на зафиксированной версии входов.
  Невыполнение STRESS у основного не запрещает выбор, но требует отдельного допустимого
  стресс-решения для готового комплекта сдачи. Не смешивать это с require_stress поискового
  профиля. Заполненность/проверка обоснования контролируются отдельно; принятый по расчётам
  вариант с незавершённым текстом остаётся незавершённым решением для сдачи.
- [ ] Фильтр по владельцу для чтения/правки/экспорта/AI-заданий; не добавлять многокомандную
  систему ролей сверх текущего auth. Совместная работа — существующий командный демоаккаунт
  либо отдельно согласованное расширение, не выдача всех записей любому пользователю.
- [ ] Импорт примера из config с `origin=example`, не автоматическое принятие основным.

### B5. API первой версии

**ГИПОТЕЗА единого prefix:** backend `/portfolio`; существующий auth `/admin/auth/*`
не меняется. При nginx `VITE_API_URL=/api` браузер вызывает `/api/portfolio/...`, proxy
передаёт `/portfolio/...`. В локальной разработке baseURL — адрес FastAPI. Не добавлять
в клиентские пути ещё один `/api`, не смешивать с прежними проектными `/api/v1/portfolio`.

- `GET /portfolio/catalog` — данные, ограничения, версии и доступные методы.
- `GET /portfolio/materials` — manifest материалов сдачи и инструкции для нижнего раздела страницы.
- `GET /portfolio/materials/{material_id}/download` — разрешённый локальный файл из manifest;
  проверка доступа и принадлежности опубликованному пакету, без произвольного filesystem path.
- `POST /portfolio/evaluate` — черновик/полный selection → расчёт и оба сценария.
- `POST /portfolio/recommend` — версия данных + метод + сценарии + epsilon + условия
  пользователя → рекомендация и альтернативы; один endpoint для свободного и ограниченного поиска.
- `POST /portfolio/compare` — явно заданные snapshots/selections → сопоставимые результаты.
- `POST /portfolio/sensitivity` — P1: selection + тип анализа + параметры → проверяемый результат.
- `POST /portfolio/scenarios/evaluate` — P1: фиксированный selection + сценарии →
  отдельные totals/checks/запасы, без автоматической замены портфеля.
- `GET /portfolio/decisions` — сохранённые решения пользователя, с пагинацией.
- `POST /portfolio/decisions` — создать решение, idempotency key против повторного сохранения.
- `GET /portfolio/decisions/{id}` — актуальный snapshot и revision.
- `PATCH /portfolio/decisions/{id}` — правка с expected_revision, включая принятие варианта.
- `POST /portfolio/decisions/{id}/export` — экспорт указанной revision; без перезаписи общих results.
- `POST /portfolio/import/preview` — проверка ограниченного JSON-снимка, пересчёт и diff;
  принятие через обычное создание решения. Не выполнять код/пути из импортируемого файла.
- `POST /portfolio/explanations`, `GET /portfolio/explanations/{id}` — только P2, §8.

422 — неверные входы/неизвестные ID; 409 — revision/dataset mismatch; 401/403 — доступ;
`no_feasible` и `no_robust_feasible` — нормальные HTTP 200 результатов поиска. Наличие нарушений портфеля — тоже
200 с checks, не серверная ошибка. Ошибки AI не превращаются в ошибки всего решения.
Ограничить размер импортов, число сравниваемых вариантов и длину текстов; конкретные лимиты
описать в OpenAPI как ограничения нашего API, не условия кейса.

Материалы выдавать эксперту по существующим демодоступам; публичную выдачу включать только
для явно разрешённого пакета, не для всех сохранённых решений. Не скачивать произвольные
URL по запросу пользователя и не превращать download в прокси/просмотр файлов сервера.
Отсутствующий материал возвращает честный статус/404, а не успешное скачивание пустого файла.

### F2. Компоновка страницы по макету

**ГИПОТЕЗА раскладки сверху вниз; проверка — desktop/mobile и сценарий §12:**

1. **Верхняя панель:** название, версия набора, «Автоподбор / Ручная проверка», настройки
   метода и основная кнопка «Подобрать портфель». В ручном режиме показываем счётчик 0/4–4/4;
   в автоматическом не требуем сначала заполнить его. Якоря ведут к сравнению и материалам.
2. **Рабочая область как на скриншотах:** каталог из восьми карточек в двух колонках слева;
   справа выбранный/рекомендуемый портфель, показатели, девять проверок. Переключатель
   просмотра BASE/STRESS расположен рядом с результатом и не запускает новый поиск сам.
3. **«Подробнее о портфеле»:** раскрываемая область под основной рабочей частью. Вклад
   каждого лота в итог, исходные и скорректированные режимом величины, формулы, источники,
   t_rep/readiness/resilience/scale и запасы. Не превращать правую колонку в длинную записку.
4. **«Альтернативы и сравнение»:** раскрываемый блок ниже, результаты и причины различий;
   при выборе другой альтернативы активный portfolio ID синхронизируется со всеми деталями.
   Здесь же «Найти с моими условиями». Следом раскрываемый блок **«Устойчивость и границы
   рекомендации»**: сценарии, худший запас, уступка по эффекту и чувствительность (F7).
5. **«Обоснование и план реализации»:** разделы-аккордеоны по лотам и общему портфелю,
   а не отдельные страницы: роли/деньги/доступ/риски/тиражирование/этапы и ответ на стресс.
6. **Действия над текущим вариантом:** сохранить, принять основным, экспортировать draft,
   опционально объяснить с Ollama. Местоположение может быть sticky-панелью без перекрытия текста.
7. **В самом конце — «Материалы решения»:** постоянный раздел для эксперта, см. F6.
   Он не исчезает при пустом выборе, ошибке подбора или недоступной Ollama.

При первом открытии подробности без результата не заполнять выдуманными данными. На узком
экране колонки перестраиваются вертикально. Якорные переходы и раскрытие деталей не сбрасывают
draft; несохранённые правки при смене активного варианта требуют сохранения или подтверждения.

#### Автоподбор в этой композиции

- [ ] Все восемь карточек загружаются из backend, числа не из макета. Каталог — входы,
  а не обязательная форма ручного отбора четырёх перед алгоритмом.
- [ ] На карточке название/архетип/группы, исходные C0/OPEX/VPUB и ссылка на детали.
  Явно подписать исходные и пересчитанные с режимом значения.
- [ ] Над результатом — метод, политика BASE/require_stress и «Подобрать»; для устойчивого
  метода дополнительно epsilon и сценарии, а не слайдеры несуществующих весов.
- [ ] После расчёта — «Рекомендованный портфель», четыре пары lot/mode, metrics/checks,
  статистика пространства, причины выбора, alternatives.
- [ ] Показывать правило; R устойчивого метода подписывать как худший нормированный запас,
  не универсальную оценку качества/вероятность. У baseline нет общего score.
- [ ] Состояния: загрузка каталога, готовность, подбор, ошибка, no_feasible,
  no_robust_feasible, результат; не путать два вида отсутствия рекомендации.
  При пустом результате не подставлять фиксированный портфель из config.
- [ ] Действия: сохранить, сравнить, изменить вручную, перейти к обоснованию.
  Переход к обоснованию прокручивает/раскрывает секцию на этой странице, не меняет маршрут.

### F3. Конструктор и результат

- [ ] В ручном режиме использовать предложенный макет: каталог слева, текущий портфель
  справа, но под ним обязательно totals и девять проверок.
- [ ] Пустое состояние предлагает запустить автоподбор либо вручную выбрать лоты.
  Частичный выбор помечается «Портфель не завершён», полный — общим итогом проверки.
  Заглушки макета не выдаются за вычисления; 0/4 не рисует нулевые финансовые показатели
  как готовый результат. На 1/4 totals и checks относятся к одному неполному выбору.
- [ ] Выбор 4/4 не означает допустимость. Кнопки «Выбрано», «Заменить», понятное удаление.
  При 4/4 остальные карточки остаются читаемыми и открываются для сравнения.
- [ ] A/B/C показывают коэффициенты и public_core; не назначать B/C выдуманные официальные названия.
- [ ] Изменения идут в отдельный draft; исходная рекомендация и принятый snapshot не мутируют.
- [ ] Переключатель просмотра BASE/STRESS меняет ограничения, не selection и не цены.
- [ ] Метрики: C0 отдельно от годовых OPEX/CASH/VPUB, KCASH, t_rep, индексы и счётчики.
  Покрытие OPEX не подписывать прибылью. `t_rep` не переименовывать в срок окупаемости.
  В компактной панели обязательно C0/OPEX/VPUB/CASH/KCASH, остальные раскрываются в
  подробностях и checks. Писать OPEX, не OPRX; использовать русские пояснения сокращений.
- [ ] Проверки: текст, факт, порог, единица, запас/дефицит; цвета только дополнительный сигнал.

### F4. Сравнение, обоснование, экспорт

Всё ниже — секции той же страницы, не обязательные вкладки или новые маршруты.

- [ ] Сравнение показывает состав/режимы каждого варианта, версии, одинаковые показатели,
  checks и дельты; исходный BASE, тот же STRESS, пересмотренный STRESS различимы.
- [ ] Автоматически не скрывать неудобные альтернативы; если сравниваются разные версии
  данных, предупредить и предложить явный пересчёт на общей версии.
- [ ] Формы обоснования — по выбранным лотам и общему решению, без сложного графового редактора.
  Показывать источник/допущение и незаполненные части; при замене лота не переносить текст
  старого лота на новый. При смене режима помечать связанное обоснование для проверки.
- [ ] Сохранение, принятие основным и экспорт — разные кнопки/операции.
- [ ] Экспорт делает backend по revision; frontend скачивает blob, не собирает финансовые
  суммы из округлённых надписей. Отдельно предупреждать об отсутствии обоснования.
- [ ] Draft можно сохранить/экспортировать с явной меткой «черновик»; принятие не означает
  экспертной проверки текста или обещания полной оценки по рубрике.

### F5. Состояние и сетевые гонки

- [ ] React Query — server state, локальная форма — draft. Ключи запросов включают
  пользователя, версии и все влияющие параметры. После выхода очищать данные пользователя.
- [ ] Любая правка делает результат stale до нового расчёта; не выдавать stale как текущий
  и не принимать/экспортировать его вместо изменённого draft.
- [ ] Сопоставлять ответы с request sequence/input hash; AbortSignal полезен, но не заменяет
  проверку актуальности. Поздний ответ режима A не должен перезаписать свежий результат C.
- [ ] Ошибки 422 привязывать к форме; не дублировать локальные и глобальные тосты.
- [ ] На 409 предлагать загрузить актуальную revision или сохранить отдельную копию.
- [ ] Keyboard/focus, текстовые подписи переключателей, контраст, читаемость чисел,
  узкий экран; UI не должен зависеть только от цвета или hover.

### F6. Нижний раздел «Материалы решения»

**ФАКТ — [README §13](../case/source/README.md):** показанное на скриншоте дерево
`src/notebooks/data/config/results/tests/docs` — рекомендуемая, не обязательная структура
репозитория. Смысл требования: эксперт быстро находит код, входы, зависимости, контрольные
результаты, документы и способ запуска. Сайт не заменяет исходники и материалы в GitVerse;
он даёт к ним удобный доступ. Не нужно перестраивать наш repo под буквальные имена из примера.

**ГИПОТЕЗА представления на странице:** не показывать пользователю дерево директорий.
Сделать компактный блок с четырьмя смысловыми группами, прямыми ссылками и скачиванием:

1. **Документы:** управленческая записка 8–12 страниц, отдельное стресс-резюме на

2. **Код и запуск:** репозиторий команды в GitVerse, README с инструкцией, расположение

   если он включён в наше решение; отсутствие notebook само по себе не является ошибкой.
3. **Данные и настройки:** неизменные разрешённые данные кейса, конфигурация выбранного
   решения, параметры метода и отдельно собственные допущения/источники.
4. **Результаты и проверка:** контрольные BASE/STRESS, выбранный портфель и сравнение,
   код тестов и инструкция их запуска. Лог последнего прогона показывать только если он
   реально есть, с версией кода/runtime и временем; наличие тестового файла не значит PASS.

- [ ] Данные раздела приходят из `SubmissionManifest`, не захардкожены в JSX. Нет готового
  файла — «Не добавлено», без фальшивой ссылки; это не мешает работать калькулятору, но
  обязательный недостающий материал отмечается как незавершённая подготовка сдачи.
- [ ] Видны версия пакета, опубликованный decision revision и commit. Ссылка на код/README
  закреплена на нужной версии, а не только на изменяемой главной ветке.
- [ ] Явно разделить «Материалы финального решения команды» и «Экспорт текущего варианта».

## 10. Этапы, зависимости и точки объединения работ

**ГИПОТЕЗА организации:** backend и frontend разрабатываются параллельно после фиксации DTO.
Это порядок работ, а не обещание конкретных часов или изменение официальных дедлайнов.

### Этап 0 — входы, метод и контракт

- Backend: B0, контроль baseline и решение упаковки, проект DTO/OpenAPI.
- Frontend: композиция одной страницы по F2, раскрываемые детали, нижний раздел F6,
  типы и контрактные fixtures без подмены реального demo.
- Вместе: утвердить ordered priorities, require_stress, `robust_epsilon_v1`, epsilon,
  определения/основания сценариев, семантику закреплений, статусы и правила versioning.
- Готово: два разработчика одинаково понимают recommend/evaluate/compare; примерный портфель
  из config нигде не объявлен результатом алгоритма.

### Этап 1 — вертикальный расчёт

- Backend: B1/B2, каталог, evaluate, упаковка зависимостей.
- Frontend: F0, каталог и ручной диагностический экран с реальными проверками.
- Готово: выбранный лот/режим меняется через UI, получаются канонические числа и причины FAIL.
  Это промежуточный этап разработки, не изменение основного пользовательского потока.

### Этап 2 — основная фича подбора

- Backend: RecommendationService, корректный cache, Парето + правило одного кандидата.
- Frontend: главный экран «Подобрать», профиль, результат, alternatives, manual fork.
- Готово: все восемь загружаются без предварительного отбора, смена правил запускает
  реальный поиск, результат детерминирован и объясним; no_feasible корректно обработан.

### Этап 3 — сравнение, сценарии и устойчивый выбор

- Backend: compare и headroom, неизменность исходного selection при смене сценария.
- Backend P1: ScenarioService, преобразования входов, R и `robust_epsilon_v1` (§4.4–4.5).
- Frontend: сравнение исходной рекомендации, ручной копии и BASE/STRESS; метод/epsilon,
  сценарии, худший запас, уступка по эффекту и `no_robust_feasible`.
- Готово: эксперт может ухудшить вариант, увидеть нарушения и вернуть исходный;
  стресс-переключатель не подменяет портфель. Запас реально участвует в выборе,
  все применённые допущения видны, официальный STRESS неизменен.

### Этап 3а — поиск с условиями и чувствительность

- Backend P1: SearchConstraints и контрольный безусловный поиск (§4.7), затем повтор полного
  подбора на сетке (§4.6). Зависит от готового устойчивого метода, не от Ollama.
- Frontend: закрепления/исключения, цена условий, параметр/диапазон анализа и интервалы
  смены рекомендации. Всё внутри сравнения и блока устойчивости одной страницы.
- Готово: ограничения пользователя соблюдаются; смена победителя отличима от потери
  допустимости; показаны точность и случаи отсутствия решения. Все четыре усиления работают.

## 12. Сквозной сценарий готовности

- [ ] Человек, не писавший код, запускает решение по README и входит демопользователем.
- [ ] Видит все восемь официальных лотов и понятную версию данных.
- [ ] Нажимает «Подобрать» без предварительного ручного выбора четырёх.
- [ ] Получает вычисленную рекомендацию и объяснение правила, а не захардкоженный пример.
- [ ] Открывает альтернативу, видит различия метрик и ограничения.
- [ ] Делает ручную копию, меняет один режим/лот, получает свежий результат и конкретный FAIL.
- [ ] Проверяет один состав в BASE/STRESS; исходная рекомендация не исчезает.
- [ ] Включает устойчивый метод, задаёт epsilon и обоснованные дополнительные сценарии;
  получает худший запас и уступку к максимуму эффекта либо честное `no_robust_feasible`.
- [ ] Проверяет текущий состав в сценариях без автоматической замены; видит факторы,
  происхождение, конкретные нарушения и отличие от официального STRESS.
- [ ] Закрепляет лот/режим или ограничивает замены, повторяет поиск и видит цену условий
  относительно свободного подбора; исходная рекомендация остаётся доступной.
- [ ] Запускает чувствительность и видит проверенный диапазон, интервалы смены победителя
  и отдельную границу допустимости. На каждой показанной точке можно повторить расчёт.
- [ ] Заполняет обоснование, сохраняет, явно принимает вариант и после reload видит то же решение.
- [ ] Экспортирует и воспроизводит его расчётом; цифры совпадают с письменными материалами.
- [ ] Не покидая основную страницу, раскрывает детализацию и обоснование; в самом низу
  находит документы, GitVerse, данные, конфигурацию, результаты, тесты и способ запуска.
- [ ] Открывает финальные PDF и исходники нужной версии. Ручное изменение портфеля не
  выдаётся за обновление уже опубликованных документов; snapshot/commit различимы.
- [ ] Отключает Ollama: подбор, сравнение, ручной расчёт и экспорт продолжают работать.
- [ ] Не требуется собственный API-ключ, платный аккаунт или помощь авторов.

**Критерий завершения:** команда может защищать конкретное решение и доказывать его расчётами;
эксперт может изменить вход и самостоятельно проверить последствия. Автоматический подбор
ускоряет выбор, но не подменяет обоснование, ответственность команды и обязательные документы.
