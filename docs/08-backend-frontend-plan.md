## 2. Итоговый пользовательский сценарий

**ГИПОТЕЗА UX; проверка — сквозной тест §12:**

1. Пользователь входит штатным способом; для эксперта команда заранее выдаёт демодоступ.
2. Приложение автоматически получает все восемь лотов, A/B/C, ограничения и версию данных.
   В первой версии не нужен произвольный CSV-upload или ручное подтверждение каждой карточки.
3. Пользователь видит правило выбора и область поиска: BASE или варианты, проходящие
   также STRESS. Выбирает профиль приоритетов и нажимает «Подобрать портфель».
4. Приложение показывает рекомендуемые четыре лота с режимами, показатели, девять проверок,
   объяснение метода, число рассмотренных/допустимых вариантов и несколько альтернатив.
5. «Изменить вручную» создаёт копию рекомендации. Замена лота/режима вызывает новый расчёт;
   исходный вариант сохраняется для сравнения.
6. Просмотр BASE/STRESS проверяет один и тот же состав. «Подобрать для других условий» —
   отдельное действие, не скрытая замена состава при переключении сценария.
7. Команда сравнивает варианты, заполняет обоснование и явно принимает основной портфель.
   «Рекомендован алгоритмом», «сохранён» и «принят командой» — разные статусы.
8. Экспортирует проверяемый снимок решения и материалы для записки.
9. По желанию нажимает «Объяснить»: Ollama оформляет факты из актуального расчёта.

## 3. Объём: что входит в первую рабочую версию

**ГИПОТЕЗА приоритетов:**

- **P0, обязательный продуктовый путь:** официальный каталог, канонический evaluate,
  алгоритмическая рекомендация, альтернативы, ручной fork, BASE/STRESS, диагностика,
  сохранение решения, формы обоснования, экспорт/воспроизведение, тесты и демодоступ.
- **P1, усиление:** объяснение конкретной замены, уже имеющийся анализ запаса, проверка
  устойчивости предпочтения, Ollama «Объяснить решение».
- **P2, только после P0/P1:** MCDA как второй метод, пользовательский D, свободные вопросы
  с ограниченным набором операций, дополнительные сценарии, улучшенное оформление отчёта.

Не входят в первую версию: разработка самих космических сервисов, новые датасеты,
ML/обучение, отдельный расчётный микросервис, универсальная договорная система,
реальные интеграции плательщиков, карты ради оформления, NPV/многолетние потоки,
Монте-Карло, произвольное изменение официальных цен, WebSocket/SSE и новая авторизация.

## 4. Алгоритм автоматического подбора

### 4.1. Каноническая часть

**ФАКТ — CSV/config и engine:** пространство стандартных комбинаций — C(8,4) × 3⁴ = 5670.
Каждый вариант — четыре уникальных лота, у каждого свой mode_id. Результаты организаторов:
C0, OPEX, VPUB и CASH суммируются, KCASH = суммарный CASH / суммарный OPEX, индексы
усредняются. SSA не увеличивает число территориальных архетипов, PNT/InSAR — одна группа.
BASE/STRESS отличаются только лимитом C0. VPUB не является денежным поступлением.

**ГИПОТЕЗА реализации:**

- [ ] Использовать все лоты из выбранной версии набора, не предварительно выбранные четыре.
- [ ] Рассчитать все пары лот/режим и все комбинации; переиспользовать существующий перебор.
- [ ] Проверить все девять условий каждого сценария, не заменять фильтрацию штрафом в score.
- [ ] Возвращать размер пространства, counts BASE/STRESS/Парето и параметры фильтра.
- [ ] Если допустимых нет, вернуть `status: no_feasible`, причины и `recommended: null`.
  Не ослаблять условия и не объявлять «наименее плохой» вариант допустимым.
- [ ] Проверки и ранжирование используют неокруглённые значения. Нынешнее округление
  в `engine/space.py:metrics_row` оставить только для отображения/старого CSV либо убрать
  из рабочего расчётного представления с регрессионной проверкой.

### 4.2. Как получить одного рекомендованного кандидата

**ГИПОТЕЗА стартового метода: `pareto_lexicographic_v1`.** Он развивает Парето из
[07-action-plan.md](07-action-plan.md) и не требует придумывать неутверждённые веса.
Проверка: ручные примеры, перестановка входных строк и сверка максимума по первому приоритету.

1. Оставить допустимые варианты в явно выбранной области.
2. Построить Парето по объявленным критериям и направлениям существующего engine:
   максимизируем VPUB, KCASH, t_rep, readiness, resilience, scale; минимизируем C0/OPEX.
3. Применить **явно упорядоченный список приоритетов**. Предлагаемый начальный профиль:
   VPUB больше → C0 меньше → OPEX меньше → KCASH больше → t_rep/readiness/resilience/scale
   больше → стабильный ID варианта. Показать этот порядок до запуска.
4. Второй критерий используется только при равенстве первого, третий — при равенстве
   предыдущих. Это не «баланс»: профиль назвать **«Общественный эффект в заданных условиях»**.
5. В первой версии сравнивать исходные неокруглённые показатели после детерминированного
   порядка суммирования лотов; допуск 1e-9 относится к каноническим ограничениям, не к
   скрытому объединению разных score. При точном равенстве всех критериев сортировать
   по стабильному ID. Это разрешает техническую ничью, а не доказывает превосходство.
6. Возвращать несколько альтернатив: следующие по тому же правилу и представители
   иных компромиссов, например меньший C0 или больший KCASH. Подписывать основание каждого.
7. Объяснение строить из фактов: первый различающий критерий, дельты, запасы и нарушения.
   Не приписывать алгоритму оценку договоров или рисков, которых нет в его входах.

**ГИПОТЕЗА политики:** первоначально `require_stress=true`, как предложено в 07: это наша
стратегия, не обязательное правило кейса. Пользователь может отдельно выполнить поиск
с `require_stress=false` в BASE и увидеть цену стресс-устойчивости. Не исключать BASE-only
варианты из каталога или ручного сравнения. Окончательные приоритеты команда утверждает
до фиксации конкурсного решения; профиль нельзя подгонять незаметно под пример из config.

### 4.3. Что именно означает «чувствительность»

**ФАКТ — [engine/sensitivity.py](../engine/sensitivity.py):** текущий модуль считает запас
до нарушения ограничений, а не изменение победителя при других предпочтениях.

**ГИПОТЕЗА реализации:** разделить две функции:

- **Запас допустимости:** сколько остаётся до порога; существующий headroom адаптировать.
  Если портфель уже недопустим, показывать дефицит, а не положительный «запас устойчивости».
- **Устойчивость выбора:** заново сравнить все варианты при другом порядке приоритетов
  или политике require_stress и показать смену рекомендации. Это не ±20% весов: у
  лексикографического метода весов нет.

Если добавляем **MCDA**, отдельно реализовать направления, нормировку с зафиксированной
базой и обработкой постоянного критерия, неотрицательные нормированные веса и их источник,
разложение score, ничьи и пересчёт при ±20% с явным правилом перенормировки. Нормировочную
базу не менять между сравниваемыми прогонами чувствительности. Не добавлять пункт MCDA
в UI, пока за ним нет алгоритма и тестов. Это расширение, не блокер первой рекомендации.

### B2. DTO и состояния

**ГИПОТЕЗА контрактов; точные схемы зафиксировать в OpenAPI до параллельной разработки UI:**

- `CaseCatalog`: dataset_id/version/hash, source refs, восемь лотов, A/B/C, BASE/STRESS,
  units, происхождение значений, перечень поддерживаемых методов и допустимых настроек.
- `SelectionItem`: `lot_id`, `mode_id`. Полный портфель — ровно четыре уникальных ID.
  Для ручного черновика API может принимать 0–4: пустой возвращает `incomplete` без
  NaN-метрик; 1–3 рассчитываются как неполные. Более четырёх, дубликаты и неизвестные ID — 422.
- `Calculation`: canonical input/hash, engine_version, per-lot detail, totals,
  checks отдельно для BASE/STRESS, `feasible_by_scenario`, годовой непокрытый OPEX.
- `ConstraintCheck`: code/title/operator/threshold/actual/unit/slack/passed/message.
  Допуск сравнений как в каноне; сериализация в стандартные JSON-типы без NaN/Infinity.
- `RecommendationRequest`: dataset_hash, method_id/version, ordered priorities,
  scenario и require_stress; четыре выбранных лота не являются обязательным входом.
- `RecommendationResult`: request/input hash, параметры поиска, counts, рекомендованный
  вариант или null, alternatives, доказуемые причины, версия правила ничьих.
- `Decision`: имя, версия, recommendation snapshot, варианты, chosen_variant_id,
  обоснование, источники/допущения, stress decision, происхождение ручных копий.
  `origin=algorithm|manual|imported|example` не смешивать со статусом принятия.
- `DecisionRationale`: per-lot потребность/роли/доступ/финансирование/закупка/риски/
  переносимость/этапы/KPI; portfolio-level стратегия, компромиссы и ответ на стресс.
- Статусы считать отдельно: `input_status`, `calculation_status`, `rationale_status`,
  `decision_status`. Непустое поле с `TODO` не считать законченным обоснованием.

### B3. Application services

- [ ] `CaseCatalogService`: загрузка одного валидированного набора и описание источников.
- [ ] `PortfolioService`: валидация selection → вызов чистого ядра → detail/totals/checks.
- [ ] `RecommendationService`: полное пространство → допустимость → метод → альтернативы.
- [ ] `ComparisonService`: один контракт сравнения двух или нескольких вариантов,
  дельты метрик и изменения checks; не перезаписывать сравниваемые входы.
- [ ] `SensitivityService`: headroom и изменения предпочтений как разные операции.
- [ ] В статистике ограничений исправить/подписать область: нынешний `binding_analysis`
  собирает отдельные checks только для BASE. Не показывать эту статистику как STRESS.
  `c0_breaking_point` — граница только по C0, не гарантия общей допустимости.
- [ ] `DecisionService`: сохранение, версии, обоснование, выбор основного и export snapshot.
- [ ] `ExportService`: CSV/JSON и человекочитаемый Markdown из одного снимка, без LLM.
- [ ] Предметные методы объяснения добавить в существующий `OllamaService`, см. §8.

Все короткие расчёты — синхронная операция HTTP без Taskiq. Не выполнять тяжёлый pandas-цикл
прямо на async event loop: сначала измерить холодный/тёплый путь; использовать предварительный
расчёт 24 пар и кеш пространства. Для API допустим thread offload чистого вызова без очереди.
Если холодный перебор действительно превышает пару секунд — прогревать версионированный кеш
при подготовке/старте и показывать readiness; не обещать мгновенность без измерения.
Фоновая задача допустима только при подтверждённой длительности, а не по умолчанию для 5670 строк.

### B4. Хранение решений

JSONB принимает только валидированную DTO, а не произвольный клиентский объект.

- [ ] Alembic-миграция, SQLAlchemy models в infrastructure, repository в core/repositories.
- [ ] Роуты вызывают сервисы; операции SQL только через repository.
- [ ] Сохранение не доверяет клиентским metrics/score: сервер считает сам и связывает
  snapshot с input hash. Изменение входов делает прошлые объяснения неактуальными.
- [ ] Оптимистическая версия: при устаревшем revision вернуть 409, не затереть чужую правку.
- [ ] Сервер разрешает принятие основным только свежего, пересчитанного полного варианта
  из четырёх уникальных лотов, проходящего BASE на зафиксированной версии входов.
  Невыполнение STRESS у основного не запрещает выбор, но требует отдельного допустимого
  стресс-решения для готового комплекта сдачи. Не смешивать это с require_stress поискового
  профиля. Заполненность/проверка обоснования контролируются отдельно; принятый по расчётам
  вариант с незавершённым текстом остаётся незавершённым решением для сдачи.
- [ ] Фильтр по владельцу для чтения/правки/экспорта/AI-заданий; не добавлять многокомандную
  систему ролей сверх текущего auth. Совместная работа — существующий командный демоаккаунт
  либо отдельно согласованное расширение, не выдача всех записей любому пользователю.
- [ ] Импорт примера из config с `origin=example`, не автоматическое принятие основным.

### B5. API первой версии

**ГИПОТЕЗА единого prefix:** backend `/portfolio`; существующий auth `/admin/auth/*`
не меняется. При nginx `VITE_API_URL=/api` браузер вызывает `/api/portfolio/...`, proxy
передаёт `/portfolio/...`. В локальной разработке baseURL — адрес FastAPI. Не добавлять
в клиентские пути ещё один `/api`, не смешивать с прежними проектными `/api/v1/portfolio`.

- `GET /portfolio/catalog` — данные, ограничения, версии и доступные методы.
- `POST /portfolio/evaluate` — черновик/полный selection → расчёт и оба сценария.
- `POST /portfolio/recommend` — версия данных + политика → рекомендация и альтернативы.
- `POST /portfolio/compare` — явно заданные snapshots/selections → сопоставимые результаты.
- `POST /portfolio/sensitivity` — P1: selection + тип анализа + параметры → проверяемый результат.
- `GET /portfolio/decisions` — сохранённые решения пользователя, с пагинацией.
- `POST /portfolio/decisions` — создать решение, idempotency key против повторного сохранения.
- `GET /portfolio/decisions/{id}` — актуальный snapshot и revision.
- `PATCH /portfolio/decisions/{id}` — правка с expected_revision, включая принятие варианта.
- `POST /portfolio/decisions/{id}/export` — экспорт указанной revision; без перезаписи общих results.
- `POST /portfolio/import/preview` — проверка ограниченного JSON-снимка, пересчёт и diff;
  принятие через обычное создание решения. Не выполнять код/пути из импортируемого файла.
- `POST /portfolio/explanations`, `GET /portfolio/explanations/{id}` — только P1, §8.

422 — неверные входы/неизвестные ID; 409 — revision/dataset mismatch; 401/403 — доступ;
`no_feasible` — нормальный HTTP 200 результата поиска. Наличие нарушений портфеля — тоже
200 с checks, не серверная ошибка. Ошибки AI не превращаются в ошибки всего решения.
Ограничить размер импортов, число сравниваемых вариантов и длину текстов; конкретные лимиты
описать в OpenAPI как ограничения нашего API, не условия кейса.

## 10. Этапы, зависимости и точки объединения работ

**ГИПОТЕЗА организации:** backend и frontend разрабатываются параллельно после фиксации DTO.
Это порядок работ, а не обещание конкретных часов или изменение официальных дедлайнов.

### Этап 0 — входы, метод и контракт

- Backend: B0, контроль baseline и решение упаковки, проект DTO/OpenAPI.
- Frontend: сценарий страниц, типы и контрактные fixtures без подмены реального demo.
- Вместе: утвердить ordered priorities, require_stress, названия статусов и правила versioning.
- Готово: два разработчика одинаково понимают recommend/evaluate/compare; примерный портфель
  из config нигде не объявлен результатом алгоритма.

### Этап 1 — вертикальный расчёт

- Backend: B1/B2, каталог, evaluate, упаковка зависимостей.
- Frontend: F0, каталог и ручной диагностический экран с реальными проверками.
- Готово: выбранный лот/режим меняется через UI, получаются канонические числа и причины FAIL.
  Это промежуточный этап разработки, не изменение основного пользовательского потока.

### Этап 2 — основная фича подбора

- Backend: RecommendationService, корректный cache, Парето + правило одного кандидата.
- Frontend: главный экран «Подобрать», профиль, результат, alternatives, manual fork.
- Готово: все восемь загружаются без предварительного отбора, смена правил запускает
  реальный поиск, результат детерминирован и объясним; no_feasible корректно обработан.

### Этап 3 — сравнение и стресс

- Backend: compare и headroom, неизменность исходного selection при смене сценария.
- Frontend: сравнение исходной рекомендации, ручной копии и BASE/STRESS.
- Готово: эксперт может ухудшить вариант, увидеть нарушения и вернуть исходный;
  стресс-переключатель не подменяет портфель.

### Этап 4 — решение и комплект данных

- Backend: migration/repository/DecisionService, import/export/revision/ownership.
- Frontend: сохранение, список решений, формы обоснования, принятие основного и скачивание.
- Продуктовая работа команды параллельно: реальные тексты, источники, финансирование,
  договорная схема, риски, тиражирование, этапы и KPI. Формы сами этого не придумывают.
- Готово: после перезагрузки решение восстанавливается; импорт экспортированного снимка

## 12. Сквозной сценарий готовности

- [ ] Человек, не писавший код, запускает решение по README и входит демопользователем.
- [ ] Видит все восемь официальных лотов и понятную версию данных.
- [ ] Нажимает «Подобрать» без предварительного ручного выбора четырёх.
- [ ] Получает вычисленную рекомендацию и объяснение правила, а не захардкоженный пример.
- [ ] Открывает альтернативу, видит различия метрик и ограничения.
- [ ] Делает ручную копию, меняет один режим/лот, получает свежий результат и конкретный FAIL.
- [ ] Проверяет один состав в BASE/STRESS; исходная рекомендация не исчезает.
- [ ] Заполняет обоснование, сохраняет, явно принимает вариант и после reload видит то же решение.
- [ ] Экспортирует и воспроизводит его расчётом; цифры совпадают с письменными материалами.
- [ ] Отключает Ollama: подбор, сравнение, ручной расчёт и экспорт продолжают работать.
- [ ] Не требуется собственный API-ключ, платный аккаунт или помощь авторов.

**Критерий завершения:** команда может защищать конкретное решение и доказывать его расчётами;
эксперт может изменить вход и самостоятельно проверить последствия. Автоматический подбор
ускоряет выбор, но не подменяет обоснование, ответственность команды и обязательные документы.
