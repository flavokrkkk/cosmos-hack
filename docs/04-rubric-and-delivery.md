## Официальный каркас оценки (Положение серии «КосмоХакатон» — ФАКТ)

Источник: https://нн.космохакатон.рф//storage/docs/regulation.pdf (публичный; файл побайтно идентичен
для всех площадок серии; прочитан 2026-09-11).

- **Тип кейса (п. 7.2):** Кейс 02 — **управленческий/продуктовый**: «разработка концепции, модели,
  регламента, дорожной карты или иного обоснованного управленческого решения». Не Data-задача →
  **автоматизированной метрики нет** (п. 14.2: спецметрики — только для Data-задач). Оценивает **жюри**.
- **Критерии (п. 14.1):** перечень, порядок и формат оценивания — по **методологии хакатона и паспорту
  кейса**. Паспорт Кейса 02 ещё не опубликован.
- **Тай-брейк (п. 14.3):** при равенстве баллов — выше оценка по **«практической применимости»**, затем
  по **«степени готовности / реализуемости решения»**. → Эти два критерия почти наверняка есть в рубрике:
  **реалистичность для РФ и рабочий инструмент — не украшение, а очки.**
- **Жюри (п. 13):** формируется по каждому кейсу; могут входить кейсодержатель (КЭП), органы власти,
  предприятия, наука; обязаны покрывать предметную, техническую и практическую составляющие; изучают
  материалы **и результаты техпроверки**, задают вопросы на защите, ставят баллы по каждому критерию
  индивидуально; итог — средний балл (п. 13.5).
- **Техническая проверка (п. 8.8, 12.4):** запуск кода, **проверка истории репозитория**,
  автоматизированная валидация, **проверка заимствований и лицензий**; результаты передаются жюри.
- **Заранее созданное и ИИ (п. 9.5–9.6, 11.1):** разрешены публичные библиотеки, модели, датасеты,
  **инструменты ИИ** и ранее созданные компоненты — при **раскрытии источников и чётком указании вклада
  команды за период хакатона**. Запрещено и ведёт к дисквалификации: выдавать готовое чужое решение за
  своё, **скрывать существенный объём заранее созданного**, привлекать незарегистрированных
  разработчиков, **подделывать результаты/метрики/демо**. Наш `PREEXISTING.md` + кейс-код отдельными
  коммитами после старта — ровно то, что требуется; **в README явно перечислить, что было до старта.**
- **Разъяснения (п. 7.5):** официальные разъяснения кейса в ходе хакатона — часть его условий. Следить
  за платформой.
- **Стоп-код (п. 8.5–8.6):** после стоп-кода репозиторий/модель/видео не менять; без обязательных
  материалов могут не допустить к защите.
- **Чек-поинты (п. 8.4):** баллы за них — только если это прямо предусмотрено кейсом. Иначе — чисто
  консультация с трекерами/экспертами (использовать!).
- **Финал (п. 16.1, 4.3, 6.8):** в финал — **первые 4 команды по каждому кейсу**; занявшие 1–4 места
  не участвуют в других окружных хакатонах.

| Презентация: ясность · выступление · демонстрация | 5+5+5 | **да** | читаемые слайды, репетиция, живое демо инструмента |

| Код и комментарии (на русском) | 3 | да | чистый движок + LLM-ручка, комментарии по-русски |
| Документация и воспроизводимость | 5 | да | README «запустил по инструкции без правок» |
| Удобство использования | 5 | да | дашборд: выбор лотов → скоркард → Парето |
| Дополнительная ценность | 5 | да | синергии, переходы режимов, «перехват» существующих бюджетных линий |

**Вывод по стратегии баллов.** Без метрики главный вес — в **обоснованности экономических решений и
защите**. Но «дешёвые» блоки (презентация ~15, отчёт ~10, код/док ~8) никуда не делись и берутся
дисциплиной, а не гениальностью. Инструмент — усилитель хорошей модели, не замена ей.

## Состав сдачи (Положение п. 9.3 — если паспорт кейса не установит иное; ФАКТ)

Команда представляет:
1. **презентацию решения**;
2. **прототип, демоверсию, макет или иной проверяемый результат** → наш инструмент (движок + дашборд);
3. **репозиторий или архив** с исходными материалами;
4. **README**: инструкция по запуску/проверке, архитектура, состав решения, использованные данные,
   библиотеки, внешние сервисы, лицензии;
5. **краткое описание практической ценности, ограничений и возможностей развития** — отдельный
   короткий документ (**не забыть**; прямо бьёт в тай-брейк «практическая применимость»);
6. демо-видео/скринкаст — **если установлено требованиями кейса** (уточнить в паспорте).

Для управленческого кейса результатом могут быть (п. 9.2): аналитическая модель, управленческое
решение, дорожная карта, методика, презентация **или их совокупность** — наш план (модель + инструмент +
отчёт + слайды) покрывает все формы. Решение должно быть **воспроизводимым и доступным для проверки**
(п. 9.4); если компонент нельзя передать — описать порядок демонстрации.

### Практика организатора (из ростовской постановки, generic)

- **Репозиторий**: понятная структура, точки входа не надо искать; кейс-специфика — отдельными
  коммитами после старта ([AGENTS.md](../AGENTS.md)).
- **README**: назначение, структура, установка, запуск инструмента и (если есть) batch-режима,
  источники данных и допущений. Максимум — если эксперт запускает по инструкции без обращения к команде.
- **Отчёт**: свободная форма, но **связка наблюдение → гипотеза → эксперимент → вывод**. «Галерея
  графиков без выводов» не считается анализом. Для Кейса 02: методология, таблица допущений (с URL),
  выбранный портфель и почему он на Парето-фронте, sensitivity, отвергнутые лоты, дорожная карта,
  риски, ограничения.
- **Презентация**: читаемость и контраст, без «простыней» текста, единая типографика и цветовая схема,
  аккуратные скриншоты инструмента, 2–3 показательных примера. Ответы на вопросы по продукту,
  модели и сценариям — отрепетированы.
- **Комментарии в коде — на русском**, содержательные (архитектура, бизнес-логика), не «воды».
- **Воспроизводимость**: зафиксированные зависимости, Docker/compose, seed/параметры модели.

## Роли под Кейс 02

- **Владелец экономики** — режимы доступа, финансирование, риски; защищает допущения перед жюри. **Критично.**
- **Билдер движка** — модель портфеля, Парето, sensitivity; LLM-ручка на `OllamaService`.
- **Фронт** — дашборд на React/TanStack: селектор лотов, скоркард, Парето-плот.
- **Питч-владелец** — отчёт, слайды, репетиция, тайминг.

## Антипаттерны (за что теряют баллы)

- **Решать «рюкзак»** (топ-4 лота под бюджет) вместо дизайна сервисной модели — теряется суть кейса.
- **Цифры без источника** / выдуманные допущения — жюри считает ТЭО профессионально.
- **Красивый UI без экономики** — инструмент усиливает модель, не заменяет.
- Не адресовать **риски и «узкое место» срока КА vs срока соглашения**, секвестр, lock-in одного поставщика.
- **Слайды-простыни**, разнобой шрифтов, нечитаемые графики — минус на ровном месте.
- **Отчёт-галерея** без выводов; README, который «запускается только у нас».
- Игнорировать **альтернативную стоимость** (что не выбрали и почему) — язык Счётной палаты.
- Все часы в модель, ноль в презентацию — потерять дешёвые ~15 баллов.
