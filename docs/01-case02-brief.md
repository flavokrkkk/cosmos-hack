[`notes/2026-09-12-reference-material.md`](notes/2026-09-12-reference-material.md).

Определения, которые важно не переврать:

| Параметр | Официальная трактовка |
|---|---|
| `territorial_archetype` | **класс** территории со схожим характером потребности, **не конкретный регион**. `Siberian` — лесные массивы с низкой плотностью наземного наблюдения; `South` — аграрные южные территории; `Central` — транспортные коридоры; `VolgaCaspian` — акватории и дельты с нефтегазовой нагрузкой; `FarEast`, `UralVolga`, `Arctic`, `Federal` — остальные |
| `capability_groups` | классы технологической базы: `EO`, `PNT/InSAR`, `SATCOM`, `SSA`. PNT, InSAR и PNT/InSAR считаются **одной** группой. Требование «≥2» — защита от технологической концентрации |
| `c0_mrub` | аналог CAPEX. В стрессе стоимость сервисов **не сжимается**: бюджет режет финансирование, а не физику сервиса |
| `opex_mrub_per_year` | аналог OPEX; «создал — и работает само» в космосе не работает |
| `anchor_cash_mrub_per_year` | якорный спрос: гарантированный платёж, покрывающий часть постоянных затрат. Конкретного плательщика файл не называет — его определяет команда (П3) |
| `vpub_mrub_per_year` | синтетическая оценка общественного эффекта: деньги, которые общество получает, но оператору никто не платит. **Не выручка**, не складывается с `cash`, двойной счёт запрещён |
| `t_rep` | «показатель воспроизводимости»; по смыслу ограничения — фильтр переносимости (П8), но **методологию придумывать за авторов нельзя** |
| `readiness` / `resilience` / `scale` | балльные индексы 1–5, методика не раскрыта. Аналогии: readiness ≈ TRL; resilience ≈ resilience engineering; **scale — именно масштабируемость/тиражируемость** |
| `federal` | `true` только у SSA; исключает лот из счётчика архетипов |
| `kcash` | покрытие OPEX поступлениями. **Не прибыль, не NPV, не ROI.** Значение ниже 1 для инфраструктуры — нормальный долгосрочный режим |

**Режимы A/B/C — учебная интерпретация кейсодержателя** (README названий не задаёт):
A ≈ преимущественно публичный сервис с госфинансированием; B ≈ сбалансированный/гибридный;
C ≈ коммерчески ориентированный подписочный B2B. Команда **обязана** раскрыть причинную цепочку:
изменение режима → организационный механизм → изменение затрат, поступлений и ценности → риск →
как проверяем допущение.

**Чего модель не считает** — фиксировать в записке обязательно: дисконтирование, NPV/IRR, срок
окупаемости, налоги, помесячную кассу, вероятностный спрос, SLA и стоимость смены поставщика,
явный горизонт планирования.

**ГИПОТЕЗА:** кейс преимущественно управленческий/продуктовый: команда проектирует портфель
и экономические правила сервисов. Проверить классификацию, метрики и обязательность прототипа
по паспорту. Общий регламент не доказывает отсутствие автоматической метрики именно в Кейсе 02.
Каркас оценки — [04-rubric-and-delivery.md](04-rubric-and-delivery.md).

- **ФАКТ: 8 модельных лотов → выбрать 4**, источник — [карточка](https://космохакатон.рф/nizhny/).
  **ГИПОТЕЗА:** лоты условные; степень привязки к реальным сервисам уточнить по паспорту.
- **Четыре группы решений на каждый выбранный лот** (прямо из карточки):
  1. **режим доступа** — общественное ядро / клуб / рынок с аварийным публичным слоем;
  2. **модель закупки и финансирования**;
  3. **распределение рисков**;
  4. **дорожная карта**.
- **ГИПОТЕЗА: режимы доступа можно интерпретировать через экономику благ.** Таблица ниже —
  рабочее толкование; определения и плательщика аварийного слоя проверить на Q&A:

  | режим | экономическая природа | кто платит | когда уместен |
  |---|---|---|---|
  | общественное ядро | общественное благо (неисключаемое, всеобщий доступ) | государство | безопасность, ЧС, базовая инфраструктура, рынок ещё не сформирован |
  | клуб | клубное благо (исключаемое, разделяемое участниками) | члены/подписчики + возможно софинансирование | отраслевые/региональные консорциумы, премиум-данные |
  | рынок с аварийным публичным слоем | частное благо + обязательство публичного доступа в ЧС (аналог USO) | рынок; публичный слой — государство | зрелый рынок с конкуренцией, но с требованием устойчивости в кризис |

- **ГИПОТЕЗА метода:** многокритериальное сравнение под бюджетом помогает обосновать выбор.
  Общая формула, веса и горизонт в карточке не заданы; проверить по паспорту.
- **ГИПОТЕЗА о ЛПР:** госзаказчик и/или регулятор, проектирующий рынок; уточнить целевую роль
  на брифинге. В прототипе решение готовит команда.

### Шесть ролей сервисной модели (обязательно развести по каждому лоту)

Источник: §6 [notes/2026-09-10](notes/2026-09-10-teammate-case02-hypothesis.md). Слабое решение пишет
«целевая аудитория»; сильное — показывает, что это **разные организации**, и рисует движение денег,
данных и ответственности между ними.

| Роль | Кто это | Зачем в модели |
|---|---|---|
| **Получатель общественной ценности** | граждане, население удалённых территорий, экстренные службы, природные территории, экономика региона | обосновывает «общественную ценность»; платит не он |
| **Пользователь** | МЧС, регион, диспетчерская, агропредприятие, страховая, телеком-оператор | задаёт требования к SLA и интерфейсам |
| **Плательщик** | федеральный/региональный бюджет, госкомпания, участники клуба, коммерческие клиенты, оператор из своих инвестиций, несколько сторон | ядро режима доступа и финансовой модели |
| **Заказчик** | тот, кто определяет требования и принимает результат | может не совпадать ни с пользователем, ни с плательщиком |
| **Оператор** | отвечает за эксплуатацию, SLA, поддержку, данные, поставщиков | носитель операционного риска |
| **Поставщики компонентов** | данные, наземная инфраструктура, вычисления, алгоритмы, ПО, поддержка | здесь живут конкуренция и lock-in |

**Ключевой момент:** несовпадение *получателя ценности*, *пользователя* и *плательщика* — это и есть
причина, по которой сервис не возникает сам собой на рынке. Режим доступа и модель финансирования —
это ответ на это несовпадение. Формулировать так и в отчёте, и на защите.
