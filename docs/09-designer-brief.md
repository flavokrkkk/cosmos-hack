# Бриф для дизайнера: путь пользователя и состояния страницы

_11.09.2026 · [База знаний](README.md) · [План backend/frontend](08-backend-frontend-plan.md)_

## 1. Что проектируем

**ФАКТ — согласованное направление:** одна основная веб-страница. Система сама рассматривает
восемь лотов и рекомендует четыре с режимами доступа. Пользователь изучает результат,
сравнивает альтернативы, при желании меняет рекомендацию вручную и фиксирует решение.
Материалы для эксперта находятся в самом низу страницы.

**ФАКТ — требования кейса:** расчёт, изменение входов, проверки, сравнение BASE/STRESS,
обоснование и доступ к материалам. Источники — [README кейсодержателя](../case/source/README.md),
§4–10, §13–14, и [критерии](../case/criteria.pdf). Автоподбор — наша функция, не обязательный
алгоритм организаторов. Заглушки на предоставленных макетах — не расчётные данные.

**ГИПОТЕЗА UX:** все описанные ниже действия, тексты и расположение блоков — дизайн-предложение.
Проверка — кликабельный прототип и сценарии §10. «Экран» далее означает состояние/фрейм
в Figma, а не отдельную страницу сайта. Авторизация может остаться отдельной страницей;
расчёты, подробности и сравнение не раскладываем по разным маршрутам.

### Пользователи и их задачи

- **Участник команды:** получить рекомендацию, проверить альтернативу, обосновать и сохранить выбор.
- **Эксперт:** открыть решение команды, повторить расчёт, изменить входы и найти документы/код.

Главный путь: открыть → подобрать → понять результат → сравнить/проверить → принять
решение → сохранить/экспортировать. Для эксперта есть короткий вход «Открыть решение команды»
из материалов, если финальное решение уже подготовлено; это не новый автоматический подбор.

## 2. Постоянная композиция одной страницы

**ГИПОТЕЗА структуры сверху вниз:**

1. **Шапка:** название «Подбор портфеля космических сервисов», версия данных, доступ к
   сохранённым решениям и якорь «Материалы». Не перегружать техническими версиями движка.
2. **Панель управления:** «Автоподбор / Ручная проверка». Содержимое панели зависит от режима.
3. **Рабочая область как на макете:** слева каталог восьми лотов, справа портфель,
   показатели и проверки. На desktop каталог в двух колонках; на узком экране — вертикально.
4. **Раскрываемый блок «Подробнее о портфеле».**
5. **Блок «Альтернативы и сравнение»**, включая поиск с условиями пользователя.
   Следом раскрываемый **«Устойчивость и границы рекомендации»**, см. U1–U4.
6. **Раскрываемый блок «Обоснование и план реализации».**
7. **Раздел «Материалы решения» в самом низу.** Всегда доступен, даже без расчёта.

Объяснение Ollama, если реализовано, открывается внутри текущего контекста — раскрываемая
область или боковая панель, не отдельный обязательный чат. Верхний якорь прокручивает
к материалам, не уводит со страницы. Нижние секции до расчёта можно свернуть/не показывать,
кроме материалов. Не заполнять пустой портфель фиктивными нулевыми итогами.

## 3. Основной сценарий: автоподбор

### A1. Первый вход, расчёта ещё нет

**Цель:** человек понимает, что ему не нужно самому выбирать четыре лота.

- Режим «Автоподбор» активен по умолчанию.
- Слева восемь исходных лотов. У карточки: название, региональный архетип, группы
  возможностей, стартовые затраты, годовые расходы и общественный эффект, «Подробнее».
- В автоподборе не показывать обязательные кнопки «Выбрать» на каждой карточке и счётчик
  «0 из 4». Все восемь уже участвуют в поиске; они не выглядят выключенными.
- Над результатом: название профиля предпочтений, «Как выбираем» и настройка
  «Подбирать только варианты, проходящие STRESS». Это настройка поиска, не переключатель просмотра.
- Стартовый профиль из плана — приоритет общественного эффекта; текст не обещает
  «идеальный баланс». Подробный порядок предпочтений раскрывается по нажатию.
- Второй метод — «Запас прочности при допустимой уступке по эффекту»: показать максимальную
  уступку по VPUB (epsilon) и набор дополнительных сценариев с факторами/основаниями.
  Начальный допуск 0; ненулевой задаётся явно. Это допуск, не вес критерия. См. U1.
- Справа краткая инструкция: «Сравним варианты из 8 лотов и предложим портфель из 4».
- Главная кнопка **«Подобрать портфель»**. Вторичное действие **«Собрать вручную»**.
- Не рисовать слайдеры весов, если в первой версии используется метод без весов.

**Переход:** нажатие «Подобрать портфель» → A2.

### A2. Выполняется подбор

- Кнопка показывает «Подбираем…», повторный запуск временно недоступен.
- Каталог и использованные настройки остаются видны.
- Справа индикатор ожидания; не показывать выдуманный процент или число обработанных вариантов.
- При повторном поиске старый результат может остаться с подписью «Предыдущий результат»;
  он не должен выглядеть новым результатом изменённых настроек.
- Предусмотреть ошибку с «Повторить». Не заменять ошибку сохранённым примером портфеля.

**Переход:** успешный расчёт → A3; отсутствие допустимых вариантов → A4.

### A3. Рекомендация получена

**Справа, сверху вниз:**

- Заголовок **«Рекомендуемый портфель»**, источник «Подобран алгоритмом».
- Четыре лота с выбранными режимами. В этой версии это просмотр рекомендации;
  изменение режима через действие «Изменить вручную» создаёт копию, не стирает оригинал.
- Пояснение в одну-две строки: какое правило дало этот выбор. Это результат алгоритма,
  не обязательный текст от Ollama.
- Компактные показатели C0, OPEX, VPUB, CASH, KCASH с понятными подписями и единицами.
- Общий статус **«Все 9 ограничений выполнены»** для просматриваемого сценария
  или конкретное количество нарушений. Ниже девять проверок, как в макете.
- Переключатель просмотра **BASE / STRESS** с подписью «Проверка этого портфеля».
- Действия **«Сравнить»**, **«Изменить вручную»**, **«Сохранить вариант»**,
  **«Подробнее о портфеле»**. Второстепенные действия не конкурируют визуально с основным.

**Слева:** в каталоге подсвечены рекомендованные лоты; остальные остаются читаемыми.
**Ниже:** статистика «рассмотрено / допустимо» из расчёта и несколько альтернатив с кратким
отличием. Не показывать вымышленный общий score или «вероятность успеха» для метода без них.

**Переходы:** детали → D1; сравнение → C1; ручная проверка → M1; сохранение → S1.
Получение рекомендации само по себе не означает, что команда приняла её основным решением.

### A4. Допустимого портфеля нет

- Сообщение **«При выбранных условиях допустимый портфель не найден»**.
- Какие ограничения отсеивают варианты — по данным backend, без придуманных причин.
- Использованные настройки остаются видны.
- Действия «Вернуться к настройкам», «Проверить вариант вручную».
- Если поиск требовал STRESS, можно явно предложить **«Искать в BASE»**, объяснив изменение
  условий. Не повышать бюджет и не отключать ограничения автоматически.
- Это не пустой портфель 0/4 и не ошибка сервера — нужен отдельный макет состояния.

## 4. Подробности и сравнение

### D1. «Подробнее о портфеле» раскрыто

Блок разворачивается под рабочей областью на той же странице. Всегда указаны активный
вариант и сценарий; при смене варианта обновляются все подробности.

- **Вклад лотов:** стартовые/годовые затраты, якорные и коммерческие поступления,
  общественный эффект каждого выбранного лота и итог портфеля.
- **До/после режима:** исходные значения и применённые коэффициенты A/B/C.
- **Дополнительные показатели:** t_rep, готовность, устойчивость, тиражируемость,
  число территориальных архетипов, групп возможностей и лотов с общественным ядром.
- **Запас и дефицит:** на сколько можно приблизиться к порогу; если уже нарушено — дефицит,
  не «отрицательная вероятность успеха». Продвинутый headroom только при готовом расчёте.
- **Откуда число:** по клику/подсказке источник, единицы, формула и допущения. Не требовать hover.

Кнопка **«Свернуть подробности»** возвращает компактный вид, но не сбрасывает расчёт.

### C1. Сравнение альтернатив

**Цель:** понять, что выигрываем и теряем при другом выборе.

- Краткие карточки альтернатив: название, состав, основное отличие, допустимость.
- Пользователь выбирает рекомендацию и альтернативу; стартовое сравнение двух вариантов
  проще читать, чем одновременно все найденные комбинации.
- Блок сравнения показывает по каждому: лоты/режимы, одинаковые показатели, проверки,
  отличия и конкретный компромисс. «Больше» не всегда «лучше»: расходы желательно уменьшать.
- Видно, является вариант алгоритмическим, ручной копией или сохранённым решением.
- «Открыть этот вариант» меняет активный просмотр, **не принимает** вариант основным.
- «Принять основным» — отдельное действие после сохранения, см. S1.
- Несовпадение версий данных — предупреждение, не скрытое сравнение несопоставимых чисел.

### U1. Устойчивый подбор вместо одной сортировки

**ФАКТ — согласованный объём:** в план включены все четыре усиления, см.
[решение команды](05-decisions.md#algorithm-upgrades-2026-09-11).
**ГИПОТЕЗА UX; проверка — прототип и тесты §11–12 [технического плана](08-backend-frontend-plan.md).**
Это дополнительные состояния той же страницы, не четыре новых маршрута.

- В «Как выбираем» коротко: «Сначала ограничиваем уступку по общественному эффекту,
  затем выбираем наибольший худший запас по ограничениям в выбранных сценариях».
- До запуска видны допуск по эффекту, официальная область BASE/require_stress и список
  дополнительных сценариев. Формула и точные настройки раскрываются, а не занимают шапку.
- После запуска рядом с рекомендацией: уступка по эффекту, худший запас, определившее его
  ограничение и сценарий, «Сравнить с максимумом эффекта». Значения и объяснение — с backend.
- Запас не подписывать «вероятностью победы», «надёжностью 95%» или универсальным рейтингом.
- Отдельное состояние **«Официальные требования выполнимы, но при выбранных сценариях и
  допустимой уступке устойчивый вариант не найден»**. Действия: изменить настройки или
  открыть базовый результат. Не подменять этим результатом отсутствующую устойчивую рекомендацию.

### U2. Дополнительные сценарии

- В раскрытом блоке устойчивости список: название, «Официальный»/«Допущение команды»,
  что меняется и на сколько, какие лоты затронуты, основание параметров.
- Официальные BASE/STRESS не редактируются. Для дополнительных сценариев — явная форма
  факторов роста расходов/снижения поступлений; совместные изменения показаны вместе.
- «Проверить этот портфель» сохраняет состав. Результаты по сценариям: показатели,
  пройденные/нарушенные проверки, запас или дефицит. «Подобрать заново» — отдельное действие.
- Доля пройденных сценариев не называется вероятностью. Без дополнительных сценариев
  писать «Проверены только BASE/STRESS», не показывать несуществующий расширенный анализ.

### U3. Когда рекомендация изменится

- Под результатами сценариев: параметр, область воздействия, диапазон/шаг, «Проверить границы».
- Результат — интервалы или компактный график: на проверенных точках рекомендуются разные
  варианты либо нет решения. Граница допустимости исходного портфеля отображается отдельно.
- По переходу видно: старый портфель нарушил ограничения **или** всё ещё допустим, но другой
  предпочтительнее. Можно раскрыть сравнение и повторить расчёт контрольной точки.
- Показывать шаг/точность, интервал между точками, состояние без смены в проверенном диапазоне,
  загрузку/ошибку и устаревший результат. Не рисовать точную границу, если backend вернул интервал.

### U4. Найти с моими условиями

- В блоке альтернатив действие «Найти с моими условиями» раскрывает компактную форму:
  включить/исключить лот, закрепить режим; при выборе исходного портфеля — максимум замен
  лотов и отдельно максимум изменений режимов. Закрепление режима включает соответствующий лот.
- Условия видны чипами и снимаются явно. Это не ручное составление готовых четырёх:
  оставшуюся часть подбирает алгоритм. Противоречия отмечаются до запуска.
- Результат рядом с поиском без условий: новый состав, режимы, дельты эффекта/расходов/запаса
  и пояснение цены условий. Показать одинаковые метод/сценарии/epsilon и соответствующие V*
  в подробностях: относительный допуск в двух поисках может означать разный абсолютный минимум эффекта.
- Если решения нет — проверенные причины и возможность снять конкретное условие.
  Не снимать автоматически. Сохранение найденного варианта не перезаписывает исходную рекомендацию.

## 5. Ручная проверка рекомендации

### M1. Ручной режим: 0/4, 1–3/4, 4/4

**Вход:** «Собрать вручную» из A1 либо «Изменить вручную» из A3/C1.

- В первом случае — пустой конструктор. Во втором — копия выбранного варианта с четырьмя лотами.
- Заголовок **«Ручная проверка портфеля»**; у копии подпись «На основе рекомендации».
- Слева появляются действия «Выбрать», «Выбрано», «Заменить»; справа — удаление и A/B/C.
- При 0/4: инструкция выбрать лоты; численные результаты отсутствуют.
- При 1–3/4: **«Портфель не завершён: выберите ещё …»**. Можно показать текущие суммы
  и проверки выбранной части, явно помеченные как предварительные, а не итоговая рекомендация.
- При 4/4: **«Все ограничения выполнены»** или **«Нарушены … ограничения»**.
  Сам счётчик 4/4 не является зелёным статусом допустимости.
- После изменения лота/режима автоматический пересчёт показывает «Пересчитываем…»;
  старые цифры помечаются как неактуальные. При ошибке — «Повторить расчёт».
- Чтобы добавить пятый лот, нужно заменить один из четырёх. Можно выбрать «Заменить»
  у нового лота и затем указать, какой убрать; весь каталог не затемняется до нечитаемости.
- Дубликаты не допускаются. Текущая рекомендация сохраняется, даже если копия стала недопустимой.

**Действия:** «Сравнить с исходным», «Сохранить как новый вариант», «Вернуться к рекомендации».
При уходе с несохранёнными правками — «Сохранить копию / Отменить изменения / Остаться».
Недопустимый вариант можно сохранить как черновик, но нельзя принять основным решением.

### M2. Объяснение режима доступа

- Нажатие на подсказку A/B/C открывает компактное описание коэффициентов.
- Видно, как режим меняет расходы/поступления/общественную ценность и учитывается ли
  общественное ядро. Договорное содержание — отдельно в обосновании.
- A/B/C не заменять неподтверждёнными названиями «бесплатный/платный».
- Режим D не рисовать как готовую функцию первой версии.

## 6. Проверка сокращения бюджета

### T1. Тот же портфель в BASE и STRESS

- Пользователь переключает **«Проверка этого портфеля: BASE / STRESS»**.
- Лоты, режимы и их стоимость не меняются. Меняется бюджетный потолок и результат проверок.
- Видны лимит, фактические затраты, запас/превышение и общий статус.
- Если проходит: **«Портфель можно сохранить при сокращении бюджета»**.
- Если не проходит: конкретная причина и действия «Изменить вручную» / «Подобрать для STRESS».

Второе действие запускает новый поиск и создаёт новый результат; это не побочный эффект
самого переключателя. Исходный портфель остаётся доступным для сравнения.

### T2. Ответ на стресс

В блоке обоснования: выбор **«Сохраняем портфель / Предлагаем пересмотр»**, пояснение
причин и последствий. При пересмотре — ссылка на выбранный стресс-вариант и сравнение
«исходный BASE / исходный STRESS / пересмотренный STRESS». Пустое пояснение — незавершённая
работа команды, не расчётная ошибка. Если основной BASE-вариант не проходит STRESS,
он может быть основным при отдельном допустимом стресс-решении для готовой сдачи.

## 7. Обоснование, сохранение и принятие

### R1. Обоснование и план реализации

Раздел на той же странице, внутри — раскрываемые карточки четырёх лотов и общий раздел.
Не показывать все поля сразу. Краткое заполненное резюме и кнопка «Редактировать» у каждого.

- **Потребность:** кто пользователь, какая проблема, что меняется благодаря сервису.
- **Участники:** получатель пользы, заказчик, плательщик, оператор, поставщики.
- **Деньги:** кто оплачивает запуск и эксплуатацию, источник покрытия дефицита.
- **Доступ и договоры:** кто и на каких условиях пользуется, за что платят исполнителю,
  кто принимает результат и отвечает за качество.
- **Риски:** что может пойти не так, ответственный, мера снижения, правило смены поставщика.
- **Развитие:** общее ядро, местная адаптация, этапы, ответственные и KPI.
- **Общее решение:** почему выбран портфель, компромиссы, источники/допущения, ответ на стресс.

Это информация команды, сохраняемая backend, не сведения, автоматически извлекаемые из CSV.
Статус «Заполнено» означает заполненность, не экспертное одобрение качества текста.
При смене лота его старое обоснование не переносится на новый. При смене режима —
пометка «Проверьте обоснование после изменения режима».

### S1. Сохранение и принятие

- «Сохранить вариант» → компактный диалог имени и комментария, затем подтверждение сохранения.
- Список сохранённых открывается в боковой панели/выпадающем списке той же страницы.
- «Принять основным» доступно для свежего полного варианта, проходящего BASE;
  недоступность сопровождается конкретной причиной. Это отдельное действие команды.
- После принятия появляется отметка **«Выбран командой»**, отдельно от расчётных статусов.
- Незавершённое обоснование/стресс-ответ остаются видимыми задачами даже после принятия.
- Правка принятого результата создаёт черновик/новую версию; опубликованные документы не меняются.
- Ошибка сохранения не очищает форму; конфликт версий предлагает открыть актуальную версию
  или сохранить копию. Экспорт указывает, какая именно версия скачивается.

### X1. Экспорт текущего варианта

- Кнопка «Экспортировать вариант» открывает выбор доступных форматов/пакетов.
- Показаны имя, версия, статус «Черновик / принятое решение» и состав выгрузки.
- Не предлагать ещё не реализованные форматы как работающие кнопки.
- Устаревший расчёт сначала пересчитывается; экспорт не должен незаметно содержать прежние числа.
- Это не кнопка автоматического создания финальной записки, презентации и публикации в GitVerse.

## 8. Помощник и материалы внизу страницы

### AI1. «Объяснить решение» — необязательная функция

- Открывается для актуального результата, показывает, какой вариант объясняется.
- Состояния: готов к запросу, объясняем, ответ, ошибка/недоступность, устаревший ответ.
- Ответ — короткие выводы и ссылки на расчётные факты; числа отображаются из backend.
- Если информации о финансировании не хватает, виден вопрос команде, не вымышленный плательщик.
- Ошибка Ollama не блокирует подбор, сравнение, сохранение или экспорт.
- Для первой версии не нужен универсальный чат с пустым полем «спросите что угодно».

### Z1. «Материалы решения» — всегда в самом низу

Раздел доступен независимо от текущего портфеля и ошибок расчёта. Верхний якорь «Материалы»
ведёт сюда. Это удобная витрина файлов/ссылок, **не дерево папок**.

- **Документы:** управленческая записка, отдельное стресс-резюме, презентация.
- **Код и запуск:** GitVerse, README, расчётная логика, зависимости и инструкция запуска.
- **Данные и настройки:** исходные данные, конфигурация решения, параметры метода и допущения.
- **Результаты и проверка:** контрольные BASE/STRESS, сравнение, тесты и инструкция проверки.

У элемента: название, краткое назначение, формат и действие «Открыть / Скачать».
Для отсутствующего обязательного файла — «Не добавлено», не фальшивая активная ссылка.
Notebook показывается только если используется. Не рисовать «Все тесты пройдены» без
реального отчёта о прогоне. Ссылки и статусы приходят с backend.

Обязательно подпись **«Материалы финального решения команды»**, версия пакета/решения
и ссылка на нужный commit. Рядом, если нужно, «Открыть решение команды» для воспроизведения.
Ручная правка наверху не меняет финальные PDF. Если пользователь исследует другой вариант,
это видно: «Вы просматриваете черновик; материалы относятся к версии …».

## 9. Общие правила для дизайна и данных

- Все лоты, режимы, числа, проверки и сохранённые пояснения приходят с backend.
  Frontend не считает вторую версию экономики. На макетах заглушки допустимы, но для
  связанного кликабельного сценария использовать согласованный набор примеров от разработки.
- C0 — стартовые затраты; OPEX — расходы за год; CASH — денежные поступления за год;
  VPUB — общественный эффект, не деньги на счёте; KCASH — покрытие расходов поступлениями.
  Сокращение плюс русская подпись; `t_rep` не переименовывать по догадке.
- Три независимые отметки: **расчёт допустим / обоснование заполнено / выбран командой**.
- «Изменить настройки поиска» влияет на следующий подбор. «BASE/STRESS» у результата
  проверяет текущий состав. Визуально разделить их назначение и не использовать два
  одинаково подписанных переключателя в разных местах.
- Не рисовать несуществующие функции: произвольный редактор стоимости, загрузку новых
  датасетов, обязательные веса, D и гарантированный PDF-генератор.
- Читаемые невыбранные карточки, контраст, фокус, текстовые статусы кроме цвета,
  доступность подсказок по нажатию, а не только hover.
- Sticky-панель не перекрывает нижние действия и материалы; accordion можно открыть
  с клавиатуры. Mobile — перестроение колонок, не уменьшенная картинка desktop.

## 10. Что дизайнер передаёт в разработку

**ГИПОТЕЗА комплекта Figma:** одна структура страницы и фреймы её состояний:

- A1 — автоподбор до запуска; A2 — loading и ошибка; A3 — рекомендация; A4 — no_feasible.
- D1 — раскрытые подробности с детализацией лотов и происхождением числа.
- C1 — сравнение рекомендации и альтернативы.
- U1 — устойчивый метод, настройки и результат с уступкой/запасом; отдельный no_robust_feasible.
- U2 — дополнительные сценарии, факторы/основания, результаты и нарушения.
- U3 — чувствительность: переходы, без смены, без решения, loading/error, точность.
- U4 — закрепления/исключения, цена условий, конфликт и отсутствие допустимого варианта.
- M1 — ручной режим 0/4, 1–3/4, допустимый 4/4, недопустимый 4/4, пересчёт/stale.
- M2 — подсказка режима и сценарий замены лота при 4/4.
- T1/T2 — тот же вариант в BASE/STRESS и выбор пересмотренного решения.
- R1 — чтение и редактирование обоснования, незавершённые поля.
- S1/X1 — сохранение, принятие, несохранённые правки, конфликт версий, экспорт.
- Z1 — нижний раздел материалов: заполненный и с недостающим файлом.
- AI1 — optional-компонент отдельно от обязательной части.
- Mobile: начальный подбор, результат с проверками, раскрытые детали и материалы.

Переиспользуемые компоненты: карточка лота, элемент портфеля с режимом, показатель,
проверка ограничения, карточка альтернативы, переключатель сценария, accordion,
действия/статусы сохранения, карточка материала, loading/error. Не создавать отдельный
компонент каждой проверки, если меняется только содержимое.

### Три обязательных кликабельных пути

1. **Автоподбор:** открыть → посмотреть правило → подобрать → изучить показатели →
   раскрыть детали → сравнить альтернативу → сохранить → принять основным.
2. **Проверка:** рекомендация → изменить вручную → заменить лот/режим → увидеть пересчёт
   и нарушение → сравнить с исходным → сохранить копию либо вернуться без потери оригинала.
3. **Эксперт:** открыть финальное решение команды → повторить расчёт → проверить STRESS →
   найти внизу записку/резюме/слайды/код и инструкцию воспроизведения.

**Дополнительный обязательный путь для согласованных усилений:** baseline → включить устойчивый
метод → задать допуск/сценарии → сравнить эффект и запас → закрепить лот/режим и подобрать
альтернативу → увидеть цену условий → проверить диапазон изменения рекомендации → сохранить
снимок с настройками. При отсутствии решения предусмотрено явное изменение условий, не скрытый fallback.

Критерий готовности дизайна: по прототипу понятно, **что выбрала программа, что изменил
пользователь, какие ограничения выполнены и какое решение команда в итоге защищает**.
