## Резюме: главные риски

1. **[ФАКТ, сборка A] Каждый подбор ждал пакетного объяснения Ollama 85–91 с и всё равно
   отдавал шаблон.** Четыре полных прогона `POST /portfolio/recommend` (STRESS ×3, BASE ×1):
   90,5 / 84,8 / 90,0 / 90,9 с, во всех `generated_by: "template"`. Причины по логу контейнера:
   дважды таймаут клиента Ollama (`ollama_service.py`, `timeout_seconds=90`), дважды
   `Ollama добавил числовые значения` — модель ответила за 84,6 с (629 токенов, 7,5 т/с), но
   валидатор `portfolio_explanation_service.py:120` отклонил текст. При `temperature=0` это
   детерминированно: на этой машине пакетное объяснение полного поиска **никогда** не проходит.
   Сборка B с `with_explanations:false` отвечает за 23–54 мс — это правильное направление; но
   второй шаг (`with_explanations:true`) по-прежнему 91–95 с и шаблон (§2.4).
2. **[ФАКТ] Режим доступа A/B/C в интерфейсе задать нельзя** — только состав лотов
   (`manualScreen.tsx`, план §14). README кейса §14, сценарий 2: «заменить один лот **или
   режим** через интерфейс». Режим меняется только через `POST /portfolio/evaluate`, CLI или
   `config/decision.json`. Риск по Т2 («часть разрешённых изменений не поддержана» — 3–4 из 5).
3. **[ФАКТ] Вариант с нарушением (Т3) в интерфейсе почти недостижим.** `recommend` возвращает
   только допустимые конфигурации; при `no_feasible` ручной режим показывает лишь счётчики
   (`manualScreen.tsx:286–304`, `NoModesBlock`) — без таблицы «условие → порог → факт → FAIL».
   Нарушение видно только косвенно: BASE-допустимый набор + переключатель STRESS
   (например `FLOOD+ENV+FIRE+INFRA`, `stress_count = 0`). Критерий Т3 прямо требует
   «эксперт проверяет допустимый вариант и вариант с нарушением».
4. **[ФАКТ] `t_rep` подписан «тиражируемость»** во фронте (`entities/portfolio/lib/compare.ts:46`
   «Средняя тиражируемость»), в опорной точке бэкенда (`recommendation_service.py:54–55`

   догадкой**». Одновременно `scale_1_5` подписан «Тиражируемость» (`format.ts:124`,

### 1.7. Хранение в браузере

**ФАКТ.** `useWorkspace` (`sessionStorage`, `workspace.ts:163–172`) хранит только входы:
режим, сценарий, условие, факт запуска, открытый вариант, лоты. Кеш React Query
(`sessionStorage`, `queryClient.ts:75–91`) хранит ответы сервера **дословно** по ключам с
`dataset_hash`; в РД второй шаг подбора помечен `persist: false`. `useSavedVariants`
(`localStorage`, `savedVariants.ts:9–22`) хранит состав, `dataset_hash`, `engine_version`,

«STRESS проходит» до пересчёта; при открытии вариант пересчитывается через `evaluate`, чужой
`dataset_hash` помечается. Подмены серверных чисел нет. **Оговорка:** снимок допустимости не
привязан к `engine_version` при том же `dataset_hash` (краевой случай; при открытии всё равно
пересчёт).

## Открытые вопросы команде

1. Оставлять ли AI-объяснение в демо, если на CPU оно всегда шаблон, а при ответе модели в срок
   его отклоняет проверка «нет цифр»? Что именно модель пишет с цифрами — залогировать.
2. Нужен ли эксперту ручной выбор режима A/B/C (README §14, сц. 2; Т2)? Если нет — как
   объяснить на защите, что «изменение режима» возможно только через `evaluate`/CLI?
3. Как показать «вариант с нарушением» (Т3) в интерфейсе при `no_feasible`?
4. `t_rep`: оставить «тиражируемость» (и в записке) или вернуть нейтральное `t_rep` до ответа
   кейсодержателя?
5. Кто и когда перед стоп-кодом обновляет `submissionManifest.ts` (GitVerse, PDF, презентация)?
6. Записать `dataset_hash` в README/записку?
7. Убрать упоминания `/admin/auth` из `backend/README.md` (тест требует отсутствия маршрутов)?
8. Переименовать экспорт `decision.json`, чтобы не путать с `config/decision.json`?

## Что не проверено

- Запуск с нуля по README (`docker compose up --build`) и сборка фронта в контейнере — запрещено
  условиями проверки.
- Двухшаговый подбор и обновлённые тексты из рабочего дерева — в браузере не смотрел.
- Поведение на touch-устройствах и мобильная вёрстка — только чтение кода.
- Содержимое ответа Ollama, отклонённого валидатором, — сервер его не логирует.
