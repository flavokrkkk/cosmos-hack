# КосмоХакатон Нижний Новгород — плейбук на победу

**Даты:** 11–13 сентября 2026 · онлайн + очная площадка в Нижнем Новгороде
**Призовой фонд:** 1,2 млн ₽ · команда 3–5 человек · финал серии — в Москве
**Организатор:** федеральный проект «Кадры для космоса» (серия из 6 хакатонов, общий фонд 7,2 млн ₽)

> **TL;DR.** Кейсы объявят на платформе события (скорее всего в день старта — на
> сайте `нн.космохакатон.рф` пока только вход). Ростовский прецедент того же
> организатора — два кейса по ДЗЗ. Мы приходим подготовленными к самому
> техничному из них — **мониторингу вегетации (NDVI)** — где 30 из 100 баллов
> берутся автоматической метрикой, и у нас уже есть **проверенный на реальных
> данных, leak-free каркас** в [`ml/`](ml/), генерирующий валидный
> submission. Это даёт фору в несколько часов и в несколько баллов.

## 0. Что мы точно знаем

- Формат и фонд НН идентичны Ростову (1,2 млн ₽). Кейсы ставят компании отрасли.
- В Ростове (4–6 сентября) было **два кейса по данным ДЗЗ**:
  - 🌱 **«Мониторинг вегетационной динамики»** (ООО «СР КМС») — ML + веб-сервис,
    автоматическая метрика. **Самый техничный и самый «выигрываемый» инженерно.**
  - 🌊 **«Чистый берег»** (ООО «СР Дата») — продуктовый: приложение/мероприятия
    для популяризации эко-анализа поверхности планеты.
- Серия идёт одним оператором, кейсодатели (СР КМС / СР Дата) повторяются →
  высокая вероятность, что вегетационный кейс появится и в НН в том же или близком
  виде. Даже если формулировка изменится, тема ДЗЗ и рубрика почти наверняка те же.

**Ставка подготовки:** 80% усилий — в вегетационный кейс (там наша фора и там
считаемые баллы), 20% — общая ДЗЗ-готовность (карта, полигоны, доступ к данным),
которая пригодится под ЛЮБОЙ из кейсов.

## 2. Кейс «Мониторинг вегетации» — победный рецепт

### 2.1 Задача в двух частях
1. **Интерполяция (оценивается автоматически, 30 б.):** восстановить `primary_ndvi`
   для контрольных строк `is_synthetic_gap=True` → `submission.csv`.
   `GapScore = round(30 * max(0, 1 − RMSE/0.10), 2)`. RMSE 0.08→6 б., 0.05→15 б.,
   0.02→24 б., 0.00→30 б., ≥0.10→0 б.
2. **Детекция аномалий (7 б., без submission):** находить негативные периоды
   угнетения вегетации и **объяснять** их (z-score к сезонной норме + погодный
   контекст). Отдельного файла ответа не требуется — только в UI и отчёте.

Плюс обязательный **веб-интерфейс**: выбор региона → готовый контур (OSM/ESA) или
свой полигон → авто-сбор данных → график исходного и восстановленного ряда →
аномалии с интерпретацией. И **две точки запуска**: веб-сервис и batch-инференс
`private_features.csv → submission.csv` (обе — по README, без правок кода).

### 2.2 Два факта данных — ПРОВЕРЕНЫ на реальном train Ростова
1. **`primary_ndvi` = первый непустой из `s2 → landsat → modis`.** Совпадение
   100.00% на 30 520 размеченных строках. Доли источников: landsat 43.5%,
   s2 36.8%, modis 19.7%.
   → источник наблюдения восстановим по дате; **разнокалиброванность сенсоров**
   (сдвиг до 0.085 при смене сенсора у соседних дат) — **главный источник ошибки
   baseline**, а не сезонная динамика. Снятие этого смещения = основной прирост.
2. **На контрольной строке скрыто ВСЁ динамическое.** У строк `is_synthetic_gap=True`
   пусты (0.0%): все индексы s2/landsat/modis, ERA5, `year`, `doy`, климатология,
   `n_reference_years`, сам `primary_ndvi`. Остаются только `anon_polygon_id`,
   `date`, `crop_type`.

### 2.3 🚨 Главная ловушка: утечка признаков (из-за неё команды теряют метрику)
Раз на контрольной строке нет ни индексов, ни погоды, ни климатологии — **модель
нельзя обучать на признаках самой строки**. Если оставить `s2_ndvi`, `era5_*`,
`ndvi_climatology_*` того же дня как признаки (как это сделано в одном из публичных
ростовских решений, `soyzy-code1`), локальный RMSE выглядит прекрасно (~0.03), но
**на платформе эти колонки пусты → модель получает мусор и разваливается**.

**Правила, чтобы не попасться:**
- Любая локальная проверка **скрывает тот же набор колонок**, что и организаторы
  (наш `make_synthetic_gaps` это делает).
- `year`/`doy`/климатология — **пересчитываются из даты**, не берутся из колонок.
- Признаки — только из **соседних видимых** наблюдений и из **даты/полигона**.
- Честный ориентир: **RMSE ~0.063 / GapScore ~11** (воспроизводимо), а не
  фантомные 0.03. Второе публичное решение (`Benzocloud/cosmohack`) сделано честно
  — его отчёт и код брать как референс.

### 2.4 Путь к GapScore (инкрементально, каждый шаг измеряем)
Наш пакет `ml/dzz` уже проходит эти ступени и печатает GapScore:

| ступень | что делает | RMSE | GapScore |
|---|---|---|---|
| baseline | среднее ближайших известных слева/справа | 0.094 | ~1.9 |
| **anchor** | снятие сенсорного смещения + гауссово сглаживание + **эффект даты** | 0.075 | **7.4** |
| **модель** | HistGradientBoosting предсказывает **остаток** от anchor | 0.070 | **8.9** |
| потолок | +контекст всех файлов, +73 признака, +ансамбль 3 seed | ~0.063 | **~11** |

- **«Эффект даты»** (средний остаток ДРУГИХ полигонов в тот же день) — второй по
  важности сигнал после anchor: в один день съёмки все участки отклоняются от своих
  кривых согласованно (общая атмосфера). Свой полигон исключаем → без утечки.
- **Модель предсказывает остаток, а не значение** — при слабом сигнале вклад → 0 и
  результат не хуже физически осмысленного anchor. Это страховка от деградации.
- **ERA5-погода почти не улучшает интерполяцию** (+0.00003) — не тратить на неё
  время ради метрики; она нужна только для **объяснения аномалий**.
- Тренировать на объединённом контексте всех выданных файлов (train + test +
  private), скрывая известные наблюдения масками; контрольные строки не трогать.

### 2.5 Веб-MVP: чеклист под баллы (не больше, не меньше)
Строим ровно то, за что дают баллы разделов 2 и 5:
- [ ] Карта (MapLibre/Leaflet) с подложкой «карта/спутник».
- [ ] **Рисование полигона** + **поиск готовых контуров** через OSM Overpass в
      текущем bbox (адаптивность под регион = не хардкодить).
- [ ] Управление набором полигонов: добавить/удалить/выбрать.
- [ ] Кнопка «Анализировать» → асинхронный job со стадиями (сбор → погода → ML →
      сохранение), UI опрашивает статус.
- [ ] График `primary_ndvi`: **исходные точки vs восстановленные** (разный стиль) +
      пропуски; погодный контекст.
- [ ] **Аномалии**: подсветка периодов (z≥−1 норма, −2≤z<−1 угнетение, z<−2
      критично), карточки с интерпретацией и **наблюдаемыми основаниями** (осадки за
      30 дней, температура) + честная пометка «гипотеза, не диагноз».
- [ ] Явные состояния: «мало данных» (`insufficient_data`) — это валидный ответ.

### 2.6 Архитектура (что переиспользуем)
Референс `Benzocloud/cosmohack` (TerraLens): React + MapLibre → Go API + очередь →
Python ML (FastAPI, HGB) → PostgreSQL; внешние источники CDSE Sentinel-2, Open-Meteo,
OSM Overpass; всё в Docker Compose, наружу только один порт. Нам НЕ обязательно
повторять стек 1:1 — можно проще (FastAPI + React + SQLite), но взять оттуда:
контракт ML-сервиса, структуру ответа (ряд + provenance + события + limitations) и
идею единого пути вычислений для веб и batch. **Один и тот же код восстановления —
и в вебе, и в batch** (иначе баллы за метрику и за демо разъезжаются).

## 7. Антипаттерны (за что штрафуют или теряют баллы)
- Утечка признаков → фантомная метрика (см. §2.3). **Проверяй локально честной маской.**
- Хардкод под один регион → минус «адаптивность». Контуры искать по bbox, не по списку.
- Разные пути вычислений в вебе и batch → демо и метрика расходятся.
- README «запускается только у нас» → минус воспроизводимость (до 5+3 б.).
- Отчёт-галерея графиков без выводов → не засчитывается как анализ.
- Комментарии в коде не на русском → критерий требует русские.
- Всё время в метрику, ноль в презентацию → теряешь дешёвые 15 баллов.
