# Космос как инфраструктура — ТЧК MISIS

Решение кейса 02 АНО «КЭП», Космохакатон, Нижний Новгород, 11–13 сентября 2026 года. Приложение выбирает четыре лота из восьми и режимы A/B/C, рассчитывает показатели по формулам организаторов, проверяет BASE/STRESS и сравнивает варианты.

**Рекомендуем [сайт команды — mogged.chillflex.art](https://mogged.chillflex.art/).** На сервере уже настроена Ollama для текстовых объяснений. Расчёты, редактирование входов, сравнение и экспорт доступны без регистрации и установки. Победителя определяет алгоритм; модель объясняет готовый результат.

## Независимый запуск

**Docker — всё приложение одной командой** из корня репозитория:

```bash
docker compose up -d --build --wait
```

Интерфейс — [localhost:5173](http://localhost:5173/), API — [localhost:5173/api/docs](http://localhost:5173/api/docs). Нужен Docker с Compose. Запускаются только интерфейс и API; `.env`, ключи, туннель и скачивание модели не требуются. Объяснения здесь формируются по расчётным шаблонам; для Ollama используйте сайт. После первой сборки расчёты работают без интернета. Остановка: `docker compose down`.

**Ноутбук — редактирование входов и проверка расчётов.** Нужен Python 3.12. Из корня репозитория или [автономного комплекта](team-submission/):

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r notebooks/requirements.txt
.venv/bin/python -m jupyterlab notebooks/portfolio_review.ipynb
```

В Windows вместо `.venv/bin/python` используется `.venv\Scripts\python.exe`. После **Run All Cells** доступны редактор восьми лотов и A/B/C, автоподбор, ручная проверка и история сравнения. Пересчёт запускается кнопкой. Сервер и Ollama не нужны, файлы исходных данных и результатов не перезаписываются.

**CLI — воспроизведение выгрузки.** В `team-submission/` установите `requirements.txt` в окружение Python 3.12, затем:

```bash
.venv/bin/python run.py recommend
.venv/bin/python run.py evaluate --snapshot /путь/team_decision_config.json
```

Если окружение ноутбука уже установлено, повторная установка не нужна. `evaluate --portfolio FIRE:A,AGRI:B,TRANS:B,ENV:A` проверяет заданный состав, `compare` сопоставляет альтернативы конфигурации, `selfcheck` проверяет расчёт и воспроизводимость. Свой конфиг: `run.py --config /путь/decision.json recommend`. Отдельная выгрузка: `run.py export --output /путь/результаты`. Готовый комплект пересобирать не требуется.

## Входы и правило выбора

Официальные входы — [case/source/](case/source/): `case_core.py`, `data/lots.csv`, `data/access_modes.csv`, `config/case_config.json`. Пользовательские изменения сохраняются отдельным снимком. В API `inputs: null` означает официальный набор; объект `inputs` содержит полные массивы `lots` из восьми лотов и `modes` из A/B/C. Формат можно взять из `GET /portfolio/catalog`; частичные изменения вместо полного снимка не принимаются.

Поля лота:

- `lot_id` — фиксированный ключ; `service`, `title` — название и подпись; `territorial_archetype`, `territory_title` — архетип и подпись. Подписи нужны API, но не участвуют в формулах.
- `capability_groups` — массив технологических групп; `federal` — признак федерального лота, который не добавляет территориальный архетип.
- `c0_mrub` — запуск, млн ₽; `opex_mrub_per_year`, `anchor_cash_mrub_per_year`, `commercial_cash_mrub_per_year`, `vpub_mrub_per_year` — расходы, две части поступлений и общественная ценность, млн ₽/год.
- `readiness_1_5`, `resilience_1_5`, `scale_1_5` — готовность, устойчивость и тиражируемость, от 1 до 5; `t_rep` — отдельный показатель кейса от 0 до 1, используемый в обязательной проверке.

У режима: `mode_id`, множители `k_c0`, `k_opex`, `k_vpub`, `k_anchor`, `k_commercial` и логический `public_core`. Денежные входы и множители неотрицательны. Полная схема и допустимые значения — в [DTO](backend/app/core/dto/portfolio.py) и Swagger.

Режим умножает соответствующие показатели лота; `CASH = anchor × k_anchor + commercial × k_commercial`. Денежные показатели суммируются, индексы усредняются. `S = CASH − OPEX`, `KCASH = CASH / OPEX`. VPUB не складывается с CASH; S не учитывает возврат C0, налоги и стоимость капитала. STRESS меняет только лимит C0.

`hybrid_maximin_v1` сравнивает VPUB, S, C0 и три индекса. Нормировка `z = (x − min) / (max − min)` строится по всей допустимой области выбранного сценария; для C0 используется обратная оценка `(max − x) / (max − min)`, постоянный критерий получает 1. Шкалы фиксируются до пользовательских фильтров, Δ и проверки чувствительности. Выбирается наибольшая минимальная оценка Q, затем больший S; дальнейшее равенство разрешают сумма оценок и стабильный идентификатор. Шкалы и порядок предпочтений — допущения команды, обоснованные в записке.

Канонические показатели не округляются. Только для ранжирования агрегаты округляются до восьми знаков, затем сравниваются точно как рациональные числа; заданный пользователем Δ повторно не округляется.

Параметры поиска: `require_stress` (по умолчанию `true`), `lot_ids` (4–8 кандидатов; `null` — весь каталог), `allowed_modes_by_lot` (разрешённые режимы; отсутствие ограничения оставляет A/B/C). API также понимает пустой `lot_ids=[]` как весь каталог; в конфигурации CLI для этого используется `null`. `budget_cap_mrub`, `vpub_floor_mrub_per_year` и `required_public_lot_ids` могут ужесточать условия кейса. `cash_loss_limit_mrub` задаёт допустимую потерю S; `null` означает Q → S без отдельного денежного предела, автоматический Δ показывает цену выбранного баланса. `quality_epsilon=0`. В API `with_explanations=false` отключает ожидание текста, сохраняя расчёт.

## Четыре файла результатов

- **`portfolio_detail.csv`** — одна строка на лот с режимом и показателями после его применения. CSV: разделитель `,`, десятичная точка, группы через `;`.
- **`portfolio_metrics.json`** — итоговые денежные показатели, KCASH, средние индексы и количества лотов, архетипов, групп, лотов ядра. Отдельного поля S нет: он равен CASH − OPEX.
- **`team_decision_config.json`** — состав, параметры, управленческие решения и допущения. В контрольной выгрузке CLI состав находится в `recommended.selection`, входы — в `algorithm_parameters.inputs`. `document_values` хранит числа документов, `export_provenance` — подписи входов, реализации и четырёх файлов.
- **`hybrid_analysis.json`** — обоснование выбора, проверки, альтернативы и чувствительность; контракт ниже.

В выгрузке UI состав записан в верхнем `selection` объектами `{lot_id, mode_id}`, входы — в `inputs`, параметры поиска — в `search_request`; сохраняются `dataset_hash`, `engine_version`, `input_hash`. CLI `evaluate --snapshot` понимает оба формата. `management_status=reference_requires_review` означает, что управленческое обоснование команды требует пересмотра для изменённого варианта. UI округляет только отображение, не экспортированные показатели. JSON сохраняется в UTF-8.

### hybrid_analysis.json, format_version = 2

- `method`, `selection_rule`, `winner` — правило и результат. У победителя: состав, S, Q, точное `q_exact` и шесть `components`. Компонент содержит `raw`, `minimum`, `maximum`, `normalized`, `direction` и признак слабейшей оценки `bottleneck`. `reference_count` — число вариантов для нормировки; `q_max` — лучший Q после условий поиска.
- `s_max_mrub` — максимум S до ограничения Δ; `cash_loss_limit_mrub` — заданный Δ или `null`; `effective_delta_mrub` — автоматическая цена лучшего Q либо ручной предел. Ручной предел может использоваться не полностью. `cash_floor_mrub` — нижняя граница S, `cash_eligible_count` — число прошедших её вариантов.
- `checks.BASE/STRESS` — проверки одного состава: `code`, `title`, `operator`, `threshold`, `actual`, `unit`, `slack`, `status` (`PASS`/`FAIL`). Отрицательный запас указывает нарушение; при нарушенном равенстве запас равен `null`.
- `search_summary` — количество рассмотренных и допустимых вариантов. В CLI `total_count`, `base_count`, `stress_count` относятся ко всему пространству, `feasible_count` — к условиям запроса, `max_q_count` — к лучшему Q до разрешения равенства по S. Область подсчёта описана в `scope`.
- `alternatives` — сравнение вариантов; `switching_curve` — интервалы Δ и их победители. Левая граница интервала включается, правая исключается; `null` справа означает отсутствие верхней границы.
- `headroom.BASE/STRESS` — запасы до порогов при отдельных изменениях входа. `null` означает отсутствие конечного относительного предела. `sensitivity` — дополнительные сценарии с повторным подбором; это не вероятности событий и не официальный STRESS. При оценке шоков на исходных шкалах оценки могут выйти за 0–1.

В **UI-выгрузке** дополнительно есть `selection_status`, `selection`, `financial` и необязательный `comparison` со входами каждого варианта. Для ручного состава или альтернативы `winner` и поля оптимальности равны `null`, кривые и чувствительность пусты. `headroom` и дополнительные счётчики полного пространства — поля CLI; UI сохраняет счётчики связанного запроса. Схема файла отличается от ответа API. Реализации: [CLI-экспорт](backend/app/core/services/portfolio_engine/export_report.py), [UI-экспорт](frontend/src/entities/portfolio/lib/snapshot.ts).

## HTTP API

Все маршруты публичные. На сайте и в Docker используется префикс `/api`; Swagger — `/api/docs`, машиночитаемая схема — `/api/openapi.json`. Прямой backend обслуживает маршруты без префикса.

- `GET /health` — состояние API и флаг включения Ollama.
- `GET /portfolio/catalog` — каталог, пороги, версии и `dataset_hash`.
- `POST /portfolio/evaluate` — `{dataset_hash, selection, inputs?}`: проверка 0–4 уникальных лотов, сразу BASE и STRESS.
- `POST /portfolio/recommend` — `{dataset_hash, inputs?, ...параметры поиска}`: рекомендация, альтернативы, счётчики и `analysis`.
- `POST /portfolio/compare` — `{variants: [EvaluateRequest, ...]}`: 2–4 полных портфеля со своими входами; разницы равны «вариант минус первый».
- `POST /portfolio/explain` — `{dataset_hash, selection, inputs?, scenario?}`: расчёт и объяснение полного портфеля.
- `POST /portfolio/compare/analyze` — `{variants, scenario?}`: объяснение сравнения. Требует разных составов/режимов; одинаковый состав на разных входах сравнивается численно через `/compare`.

`dataset_hash` берётся из каталога, `input_hash` идентифицирует расчёт с его входами и версией движка. Ответ `Calculation` содержит собственные `inputs`, `selection`, построчный `detail`, итоговые `metrics`, `financial`, `checks`, `feasible_by_scenario`. `financial.annual_surplus_mrub` — S. В API проверки используют `passed`, в файле экспорта — `status`.

`status=complete` означает полный состав, а не выполнение ограничений. У пустого состава `metrics=null`. Если подбор невозможен, возвращается `status=no_feasible`, `recommended=null`, `alternatives=[]`; условия не ослабляются. Нарушения кейса возвращаются с **HTTP 200**, несовпадение версии — **409**, неверные входы, включая неопределённый KCASH при нулевом OPEX, — **422**. Формат ошибки FastAPI — `detail`.

Объяснения помечены `generated_by=ollama|template`, `model` и `warning`. Сбой модели не меняет расчёт. Клиент передаёт входы, а не готовые метрики. Сохранённые варианты живут в браузере и содержат свои снимки данных; backend их не хранит.

## Технические критерии Т1–Т5

Соответствие [критериям](case/criteria.pdf), с. 6–7:

- **Т1 — расчёт.** Неизменённый [case_core.py](case/source/case_core.py), общий движок для всех способов запуска, полный перебор и детерминированный выбор; self-check сверяет формулы и воспроизводимость. Ollama не участвует в вычислениях.
- **Т2 — входные данные.** Поля лотов и коэффициенты режимов редактируются без правки кода. После изменений запускается новый расчёт; оригинальные данные сохраняются отдельно.
- **Т3 — ограничения.** Для всех девяти условий показаны факт, порог, направление, запас и результат. Используется канонический допуск `1e-9`; количественная проверка отделена от управленческих допущений.
- **Т4 — сравнение.** Составы, входы, показатели и разницы сопоставляются в UI, ноутбуке и API/CLI. BASE/STRESS проверяются на одном составе; новый подбор выполняется отдельно.
- **Т5 — воспроизводимость.** Предоставлены код, данные, конфигурация, фиксированные зависимости и готовый комплект. Docker и ноутбук работают без ключей и участия команды; выгруженный снимок можно воспроизвести через CLI.
