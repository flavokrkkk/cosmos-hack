# Generic-ядро под любой ДЗЗ-кейс с метрикой

`dzz/` построен так, чтобы подходить не только под вегетацию, а под **любую
ДЗЗ-задачу вида «восстановить скрытые значения временного ряда → RMSE»**
(влажность почвы, уровень/качество воды, снег, температура поверхности и т.п.).
Тема входит в **один модуль** (`dzz/config.py`), остальное не меняется.

## Что переносится без изменений (~80%)

| Компонент | Модуль | Почему generic |
|---|---|---|
| Канонизация колонок кейса | `dzz/data.py` | имена берутся из CaseConfig |
| **Честная маска** (synthetic gaps) | `dzz/masking.py` | любой «Метрика»-кейс прячет строки |
| Метрика + строгий валидатор | `dzz/metrics.py` | формула/порог — параметры конфига |
| Baseline, anchor, модель, ансамбль | `dzz/reconstruct.py` | опираются на соседей и календарь, не на тему |
| Признаки leak-free | `dzz/features.py` | универсальны для «значение на объект во времени» |
| Аномалии (z-score к норме) | `dzz/anomalies.py` | работает с любым индексом vs его норма |

Внутри всё работает с **каноническими** колонками: `anon_polygon_id`, `date`,
`target`, `sensor`, `doy`, `year`. Ни одной привязки к NDVI в логике не осталось.

## Что заполняешь под кейс (~20%) — только `dzz/config.py`

```python
CaseConfig(
    id_col=...,           # идентификатор объекта
    date_col=...,         # дата
    target_col=...,       # что восстанавливаем (цель метрики)
    pred_col=...,         # имя предсказания в submission (см. формат в ЛК)
    control_flag_col=..., # флаг контрольных строк (или None)
    source_cols=...,      # если цель = смесь сенсоров: [(колонка, имя), ...]; иначе None
    static_cat_col=...,   # статический категориальный признак (или None)
    metric_threshold=..., # порог GapScore из регламента
)
```

`data.prepare(df, cfg)` приводит эти колонки к каноническим, и весь код работает
как есть. `VEGETATION` — заполненный пример, рядом пустой `TEMPLATE`.

## Первые ~2 часа на хакатоне (кейс с метрикой)

1. Скачать данные, посмотреть схему (список колонок).
2. Заполнить новый `CaseConfig` в `dzz/config.py` под реальные имена; в CLI
   поставить `CFG = <твой_конфиг>`.
3. `python ml/local_eval.py --data <train> --model` → честная цифра RMSE/GapScore.
4. `python ml/make_submission.py --context <train> --test <test> --out submission.csv --ensemble`
   → валидный submission, грузим на платформу как можно раньше.
5. Дальше двигаем метрику признаками (`dzz/features.py`), аномалии — `dzz/anomalies.py`.

## Где generic-ядро НЕ подходит напрямую

- **Если метрика не «восстановить значение», а детекция/классификация** (пиксели
  пожара, change-detection с F1/IoU) — регрессионное ядро (anchor + HGB на остаток)
  не применяется напрямую. Переносятся: канонизация, честная маска, валидатор,
  каркас признаков; меняется «голова» на классификатор (несколько часов).
- **Правило источника** (`source_cols`) специфично: в вегетации цель = первый
  непустой из s2→landsat→modis. В теме без смеси сенсоров — `source_cols=None`,
  и признаки про источник просто выключаются.
- **Веб-режим** (сбор спутниковых данных под полигон) — отдельная от ядра
  инженерия (CDSE/GEE), но тоже переносится между темами.
